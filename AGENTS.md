# Xray VLESS + REALITY + XHTTP — инструкции для агентов

Личный VPN на VPS. `setup.sh` — первая установка, `xm.sh` — менеджер (на сервере
`/usr/local/bin/xm`, команды — `xm help`). Цель любой правки — в таком порядке при конфликте:
1) не выделяться для ТСПУ (стабильность входит сюда: обрыв — подпись прокси; утечка адреса
сервера через локальный SOCKS или сервисы, ищущие VPN, — тоже: найденный адрес банят);
2) анонимность; 3) скорость; 4) удобство. Уступка нижнего верхнему — с названной ценой;
пункты «Что видит противник» и режимы цензора — `xray-dpi/SKILL.md`, «Критерий».

## Всегда

- Отвечать на русском.
- Любая работа по Xray, DPI, сети, серверу, клиентам, `setup.sh`/`xm.sh` — по скиллу
  `xray-dpi` (`.claude/skills/xray-dpi/SKILL.md`): загрузить до первого ответа.
- Три ответа на задачу: первый — «Готово, когда:» (1–3 проверяемых условия) и «Вне задачи:»,
  затем полное решение; второй — все недочёты разом; третий — финальный; с четвёртого новых
  проверок нет; нерешённое — в журнал сервера. Регламент и шаблон — скилл `task-completion`.
- Репозиторий ≠ сервер. Код показывает, что должно быть; что есть — только вывод команды
  с живого VPS. Расхождение — норма: не прогнан `xm self-update`, ручная правка, другая
  версия пакета.
- Команды, которым нужны права, — с `sudo`: владелец работает не под root.
- Объём правки = объём задачи: без «заодно», рефакторинга соседнего кода и опций на будущее.

## Ответ: коротко и с вердиктом

Краткость сокращает текст, а не работу: ветки «если видишь X — примени A», варианты с ценой,
чек-лист `xray-dpi` и запись в журнал — по скиллам, это не «лишнее». Правила проекта,
безопасности и системные инструкции — выше этого раздела.

- Сразу суть: без вступлений, пересказа задачи, повторов и очевидного; тезисы вместо абзацев.
  Ход рассуждений не выводить — выводы, факты, обоснования, действия. Подробности — по
  запросу или когда без них решение неверно.
- Формат — минимально достаточный: простой вопрос — одна-две фразы; ошибка — причина,
  исправление, проверка; техническая задача — результат, изменения, команды проверки.
  Каркас по умолчанию — «Результат / Действия / Замечания / ИТОГ», пустые разделы не писать.
- Замечания — только существенные: что не так, чем важно, что нужно для устранения.
- Нужно действие владельца — копируемый блок команд под его ОС и оболочку, связанные — одним
  блоком; после блока — ожидаемый результат. Разрушительное или необратимое — риск и
  предварительная проверка до команды.
- Не хватает данных — минимум конкретных вопросов: что нужно, зачем и команда, которая это
  покажет (порядок — `task-completion`). Можно продолжить с обоснованным допущением —
  продолжать и назвать его.
- Не писать: необязательные советы и альтернативы, резюме в конце, предложения продолжить,
  один вывод в двух местах.
- Подтверждённое, предположение и непроверенное — раздельно. Без проверки задача не
  объявляется выполненной; команда, вывода которой нет, не считается выполненной.
- Последняя строка содержательного ответа — вердикт с кратким обоснованием:
  - `ИТОГ: OK` — сделано и проверено, замечаний нет;
  - `ИТОГ: OK С ОГОВОРКАМИ` — работает, но есть названные ограничения или непроверенные условия;
  - `ИТОГ: НУЖНЫ ДАННЫЕ` — без данных от владельца не продолжить;
  - `ИТОГ: ПРОБЛЕМА` — ошибка, блокер или невыполненное требование.
- Ответ с PR или правкой репозитория вместо `ИТОГ` кончается отчётом: по строке на поле,
  `merge_ready` последней. Выше — только что изменено (тезисы) и команды владельцу, если нужны;
  подробности — при провале или по запросу.

  ```
  code_pr: PASS
  checks: PASS
  integration: NOT_REQUIRED
  merge_ready: YES
  ```

  - `code_pr` — изменённый код делает то, что должен: целевые проверки правки PASS | FAIL |
    NOT_RUN (не запускались).
  - `checks` — `bash tests/check.sh` на текущем коде: выход 0 — PASS.
  - `integration` — PASS | FAIL | NOT_REQUIRED | NOT_RUN | BLOCKED; нужна ли — уровень по
    `verification.md` §0. NOT_REQUIRED — нижний уровень доказывает эффект, а не «не успел».
  - `merge_ready` — YES: code_pr и checks PASS, integration PASS или NOT_REQUIRED, существенных
    непроверенных рисков нет; NO: что-то FAIL или найдена проблема; иначе UNKNOWN.
  - Значение — только по выводу проверки, запущенной на текущем коде; не PASS / NOT_REQUIRED /
    YES — с причиной в несколько слов через « — ». Строки `<что>: expected=…, actual=…` и
    `differences` — из вывода скрипта на VPS и только когда относятся к правке.

## Публичный репозиторий: данные установки — никогда

В код, комментарии, README, коммиты, PR и файлы скиллов и правил не попадает ничего, что
идентифицирует установку: профиль, собранный из мелочей, сам по себе утечка.

- IP сервера, хостер, домены владельца; UUID, ключи и shortId REALITY;
- фактические порты установки, если они не дефолтные;
- вывод команд с сервера как есть (логи, `ss`, `journalctl`, дампы);
- сторонние службы владельца на том же VPS — только нейтрально: «служба на UDP с тем же номером».

Примеры — `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` (RFC 5737), `example.com`.
Деталь сервера, которую надо сохранить между сессиями, — `sudo xm journal add "…"` на VPS.
Перед каждым коммитом — `bash tests/check.sh` (в Claude Code его запускает хук на `git commit`
и `git push`): IP вне документационных сетей, петли, частных сетей и публичных резолверов и UUID
в коммитах ветки, индексе и рабочем дереве — провал. Убрать, а не обходить.

## Код, проверка, публикация

- `setup.sh` идёт под `set -euo pipefail` (пустой `grep` роняет конвейер), `xm.sh` — без
  него. Правила правки обоих — `.claude/rules/bash-scripts.md`.
- `xm.sh` и `setup.sh` — большие файлы: целиком не читать (правило по путям подгрузится только
  после первого чтения). Сначала карта, потом Read с offset/limit по нужному диапазону: xm.sh —
  `grep -nE '^# ─── |^[a-z][a-z|-]*\)' xm.sh | sed -E 's/ (─)+$//'` (разделы и команды),
  setup.sh — `grep -nE '^[a-z_]+\(\)|^ *header ' setup.sh` (функции и шаги), функция —
  `grep -n '^имя()' xm.sh`.
- Уровень проверки — наименьший, который доказывает эффект правки
  (`.claude/skills/xray-dpi/references/verification.md` §0): живой VPS — только когда эффект
  зависит от состояния сервера, сети или клиента. Тогда в PR — скрипт `tests/vps/<тема>.sh` на
  `tests/lib.sh`: он сам сравнивает ожидаемое с фактическим и печатает отчёт, запускает его
  владелец. Не прогнан — `integration: NOT_RUN` и строка в `.claude/HANDOFF.md` §3.1.
- Тест кода доказывает эффект этой правки, а не даёт зелёный прогон: с откаченной правкой
  проверка эффекта падает. Мок — только там, где подменяемое не предмет проверки; эффект в
  поведении системы — реальная проверка, владельцу — одной командой. Правила —
  `.claude/rules/tests.md`.
- README, тело PR, коммиты — `.claude/skills/xray-dpi/references/publishing.md`: тело PR —
  только перечень добавленного, без упоминаний ассистента и ссылок на сессии; «почему» —
  в теле коммита.

## Инструкции меняются вместе с кодом

Правка кода, после которой скиллы или правила говорят неправду, не закончена. В той же правке:

- новая или изменённая команда, флаг, путь на сервере → `xm help`; `xray-dpi/SKILL.md` —
  только если меняется порядок работы или контекст установки (каталог команд там не ведётся);
  `verification.md` — если меняется снимок состояния или способ доказать эффект;
- код опирается на версию Xray, порог, умолчание или поведение ТСПУ →
  `xray-dpi/references/landscape.md` с датой и источником; комментарий в коде с ним не расходится;
- разбор дал обобщаемый вывод → строка в `xray-dpi/references/lessons.md` и разбор в
  `lessons-detail.md`;
- изменилась сама процедура работы → соответствующий скилл или этот файл.

Как править сами инструкции — `.claude/rules/agent-instructions.md`.

## Где что

- `.claude/skills/xray-dpi/` — экспертиза DPI/ТСПУ/Xray, порядок работы, справочники.
- `.claude/skills/task-completion/` — бюджет ответов, уточняющие вопросы, шаблон записи в журнал.
- `.claude/rules/` — правила, нужные при правке определённых файлов.
- `tests/` — `check.sh` (обязательные проверки), `lib.sh` (харнесс скриптов
  `tests/vps/<тема>.sh` для живого VPS), тесты хуков и харнесса.
- `.claude/HANDOFF.md` — открытые вопросы, снятые гипотезы и долг: с него продолжать прошлую
  работу, читая только разделы по теме задачи. Сделанное — в git и PR.
- На сервере: журнал установки `/usr/local/etc/xray/journal.md` (`sudo xm journal`) — только там.
