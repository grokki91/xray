# Xray VLESS+REALITY+XHTTP — Auto Setup

Автоматическая установка Xray-core с VLESS+REALITY+XHTTP на Ubuntu 22.04.
После установки доступен менеджер `xm` для управления сервером.

---

## Требования

- Ubuntu 22.04 LTS (чистый VPS)
- Пользователь с `sudo` или root
- SSH настроен, вход по root отключён

---

## Быстрый старт

Заходишь на VPS по SSH и одной командой скачиваешь + запускаешь установку:

```bash
sudo git clone https://github.com/grokki91/xray.git /opt/xray && sudo bash /opt/xray/setup.sh
```

`setup.sh` и `xm.sh` должны лежать рядом — скрипт это использует. `/opt/xray` вместо домашнего каталога взят намеренно: путь стабильный, не зависит от того, под каким пользователем ты зашёл, и `sudo xm self-update` найдёт его сам. Клонировать можно куда угодно, `setup.sh` запомнит фактический путь.

Дальше скрипт задаст несколько вопросов интерактивно:

| Параметр | Что это | Рекомендация |
|---|---|---|
| **SNI / dest** | Домен, под который «маскируется» сервер. REALITY прозрачно форвардит TLS-хендшейк на этот сайт всем, кто не знает правильный ключ — со стороны выглядит как обычный визит на этот домен | `www.apple.com` — компактный сертификат, стабильный хендшейк |
| **HTTP path** | Путь запроса в XHTTP-трафике (имитирует обращение к статике/видео/API реального сайта). На безопасность не влияет, помогает скрыть паттерн трафика | любой из готового списка |
| **Режим XHTTP** | `auto` — сервер сам выбирает HTTP/1.1 или HTTP/2, подходит почти всегда. `stream-one` — один долгоживущий поток, иногда быстрее, но менее гибкий в плохих сетях | `auto` |
| **uTLS fingerprint** | Какой браузер имитирует TLS-отпечаток клиента, чтобы DPI не отличал xray от обычного браузера | `chrome` — самый массовый трафик, лучше всего сливается с фоном |
| **Порт XHTTP** | Порт, на котором сервер слушает основной трафик | `443` — стандартный HTTPS, меньше всего подозрений |
| **TCP inbound (XTLS-Vision)** | Необязательный второй способ подключения на отдельном порту, другой транспорт (raw TCP вместо XHTTP). Полезен как запасной канал, если основной вдруг перестанет работать у части клиентов/сетей | по желанию |

По окончании скрипт выводит VLESS URI **и QR-код прямо в терминале** — сканируй с телефона, не набирая руками. Все данные сохраняются в `/usr/local/etc/xray/client-info.txt`.

## Обновление

`setup.sh` — только для первой установки. Дальше всё делает `xm`, и ничего
руками править не надо: источник правды — репозиторий.

```bash
sudo xm self-update          # подтянуть коммиты и переустановить xm
sudo xm self-update --check  # только посмотреть, есть ли что нового
```

Команда находит git-чекаут (по записи в `/usr/local/etc/xray/xm-source`, затем
в `/opt/xray`, `/root/xray`, `/home/*/xray`), делает `git fetch`, проверяет
новый `xm.sh` на синтаксис, кладёт бэкап текущего в `backups/` и заменяет
`/usr/local/bin/xm`. **Кроме этого файла не трогает ничего.** В конце
показывает, что ещё стоит обновить: версию Xray-core, geo-базы, непринятые
анти-DPI настройки.

Если чекаута на сервере нет или он не тот — укажи явно:

```bash
sudo xm self-update --from https://github.com/grokki91/xray.git   # склонирует в /opt/xray
sudo xm self-update --from /путь/к/чекауту                        # возьмёт существующий
```

Незакоммиченные правки в чекауте останавливают обновление — чтобы не потерять
их молча. Либо `git stash`, либо `sudo xm self-update --force` (выбросит).

Полный цикл обновления сервера:

```bash
sudo xm self-update     # менеджер
sudo xm update          # Xray-core
sudo xm update-geo      # geoip.dat / geosite.dat
sudo xm harden          # применить свежие анти-DPI настройки
sudo xm diag-dpi        # проверить, что получилось
```

Ключи, UUID и выданные клиентам URI при этом не меняются.

## Повторная установка

```bash
sudo bash setup.sh --reinstall
```

**Это не способ обновиться.** Переустановка генерирует новые ключи REALITY —
все выданные URI и QR-коды умирают — и переписывает общесистемные вещи:
`nginx.conf`, `sites-enabled`, весь `stream-enabled/`, `ufw`, `fail2ban`.
Если на этой же машине живёт что-то ещё, оно может встать. Скрипт покажет
`xm neighbors` и потребует ввести подтверждение словом.

Чтобы обновиться — `sudo xm self-update`, см. раздел выше.

## VPN не один на сервере

Когда рядом крутится что-то своё — бот, сайт, API:

```bash
sudo xm neighbors
```

Показывает чужие nginx-vhost'ы, кто занимает какие порты, кастомные
systemd-юниты, правила UFW — и отдельным блоком то, что трогает каждая
команда `xm`. Плюс ловит конкретный конфликт, который валит nginx целиком:
`default_server` на `:80`, объявленный дважды (у нас и у соседа) — тогда
`nginx -t` падает и не поднимается ни один сайт.

Что безопасно при соседях: `xm self-update` (только свой бинарь),
`xm harden` и `xm set-sni` (перезагружают nginx, но только после успешного
`nginx -t`), `xm update` (только xray), все `xm diag*` (ничего не меняют).
Опасно ровно одно — `setup.sh --reinstall`.

## Управление: xm

Запускать от root или через `sudo`.

### Сервис
```bash
xm start / stop / restart / status
```

### Клиенты
```bash
xm add [имя]                # добавить клиента (алиас: add-client)
xm del                      # удалить клиента по UUID (алиас: del-client)
xm clients                  # список клиентов
xm uri [имя|--tcp|--all]    # VLESS URI
xm qr [имя] [--tcp|--both|--all]   # QR-код в терминал (по умолч. — выбор клиента)
```

### Второй inbound (XTLS-Vision/TCP)
```bash
xm add-tcp                  # добавить TCP inbound, клиенты копируются автоматически
```

### Конфиг, домен-маска, бэкапы
```bash
xm edit                     # открыть конфиг в nano (автобэкап перед открытием)
xm test                     # проверить валидность конфига
xm apply                    # проверить + перезапустить xray
xm set-sni <domain>         # сменить домен-маску сразу везде (config + nginx), с проверкой сертификата и откатом
xm backup / restore / backups
```

### Обновление
```bash
xm self-update              # обновить сам xm из git-чекаута репозитория
xm self-update --check      # только показать, есть ли новые коммиты
xm self-update --from <url> # указать/сменить источник (склонирует в /opt/xray)
xm update [--check]         # обновить Xray-core (--check — только сравнить версию)
xm update-geo               # обновить geoip.dat / geosite.dat
```

### Анти-DPI и анонимность
```bash
xm harden                    # DoH на сервере + перехват :53 + mimic-fallback
xm harden --check            # только показать текущее состояние
xm harden --off              # откатить
xm pq status | on | off      # ML-DSA-65: post-quantum подпись REALITY
```

### Диагностика
```bash
xm selftest [--tcp|--all]    # живой хендшейк через loopback — начинай с неё
xm diag                      # полная диагностика — запускай первым при проблемах
xm diag-dpi [--quick]        # устойчивость к DPI: зонды, DNS-утечки, профиль трафика
xm sni-scan                  # замер доменов-масок (cert / h2 / RTT)
xm reality-debug on|off      # почему REALITY отказывает (авто-off через 15 мин)
xm diag-ntp                  # синхронизация времени (критично для REALITY)
xm diag-ports                # открытые порты и слушатели
xm diag-tls                  # TLS сертификат и fingerprint
xm diag-fw                   # firewall и статус банов
xm diag-log                  # анализ лога на ошибки
xm neighbors                 # кто ещё живёт на сервере и что трогает xm
```

## DNS: почему это отдельная тема

С августа 2025 массово сообщают об ограничениях **DoH и DoT** у российских
операторов — Google DNS через `dns.google` / `8.8.8.8`, Cloudflare через
`1.1.1.1:853` и далее по списку. Насколько это системно и надолго — со стороны
сервера не проверить, да и не нужно: утечки из таблицы ниже существуют
независимо от этих сообщений, блокировка DoH просто делает их массовыми.

Сам VPN такая блокировка не ломает: VLESS-тоннель работает по-другому.
Ломается **логика клиента** — браузер или ОС, не достучавшись до Secure DNS,
молча откатывается на обычный DNS. Дальше вопрос только в том, кто увидит имя
домена.

| Ситуация | Кто видит имя домена | Закрыто? |
|---|---|---|
| VPN выключен, Secure DNS зарезан | провайдер, и он же может подменить ответ (НСДИ) | нет — тут поможет только включённый VPN |
| VPN включён, на сервере нет `dns`-блока | хостер VPS: Xray резолвит системным резолвером открытым текстом | **да**, `xm harden` |
| VPN включён, клиент шлёт plain-DNS в тоннель | внешний резолвер и все на пути от VPS до него | **да**, `xm harden` (перехват `:53`) |
| VPN включён, `dns`-блок есть, но Xray всё равно ушёл в системный резолвер | все на пути от VPS до резолвера — пока системный резолвер без DoT | **да**, `xm harden` (DoT на стабе); саму причину ловит `xm diag-dpi`, тест E5 |

Последняя строка — не теория: она получена замером на живом сервере. Атрибуция
по UID (`iptables -j LOG --log-uid`) показала запросы к `127.0.0.53` от UID
процесса Xray на имя, которое существовало только внутри теста, — то есть
`dns`-блок в конфиге сам по себе не гарантирует, что резолвит именно он.
Поэтому `harden` закрывает не только путь Xray, но и сам системный резолвер.

`xm harden` делает четыре вещи:

1. **DoH на сервере.** В конфиг добавляется `dns`-блок с резолверами, заданными
   IP-литералом (`https+local://1.1.1.1/dns-query` и др.) — так нет
   bootstrap-запроса «а какой IP у dns.google», который ушёл бы открытым.
   Резолверы проверяются на доступность **до** правки конфига: включить DoH,
   до которого VPS не дотягивается, значит убить резолвинг без единой ошибки
   в логе.
2. **Перехват `:53`.** Любой DNS-запрос, прилетевший в тоннель, сервер
   обрабатывает сам и отвечает из своего DoH. Клиенту настраивать ничего не
   надо, и блокировки DoH/DoT у провайдера на него больше не действуют, пока
   VPN включён.
3. **Системный резолвер на строгий DoT.** `systemd-resolved` переводится на
   `DNSOverTLS=yes` с пустым `FallbackDNS`. Строгий режим и пустой fallback
   здесь принципиальны: при `opportunistic` или с непустым `FallbackDNS`
   резолвед при недоступном `:853` молча уходит в открытый UDP — та же утечка,
   но уже без единого признака. Заодно `resolver` в nginx-fallback переезжает
   с `1.1.1.1 8.8.8.8` на `127.0.0.53`: раньше nginx каждые `valid=30s` слал
   открытый UDP-запрос за адресом домена-маски мимо всех остальных настроек.
   Если `:853` у хостера зарезан, шаг откатывается сам и остальные продолжают.
4. **mimic-fallback в nginx.** Зонд с чужим или пустым SNI получает ответ
   настоящего сайта-маски вместо молчаливого обрыва TCP. Обрыв — это готовая
   подпись «порт открыт, TLS не говорит», по которой сканер отделяет прокси от
   веб-сервера за один коннект. Открытым SNI-релеем сервер при этом не
   становится: адрес назначения — константа, извне его не выбрать.

Новые установки получают всё это сразу. Для уже работающего сервера:

```bash
sudo xm harden          # применить (ключи и клиенты не меняются)
sudo xm diag-dpi        # проверить эффект
```

Проверить утечку DNS отдельно (`xm diag-dpi`, блок E) — там два живых теста:

* **E4** — запрос на заведомо мёртвый резолвер `192.0.2.1` (RFC 5737): ответ
  физически может прийти только от перехвата на сервере, так что тест бинарный.
* **E5** — два имени через свой же тоннель под `tcpdump`: заведомо живое
  (`one.one.one.one`) и заведомо несуществующее. Разница между ними и есть
  диагноз. Течёт только несуществующее — сервер уходит в системный резолвер
  лишь когда DoH не разрешил имя; течёт и живое — своим DoH он не пользуется
  вообще. Запросы шлются SOCKS5 с `ATYP=DOMAIN`, поэтому сам тест резолвить не
  может по построению, а дамп классифицируется по адресу источника: ушло на
  провод / спросили локальный стаб / запроса не было. Это три разные вещи, и
  «хостер видит домены» верно только для первой.

Найти утечку, которую `harden` закрыть не может, — отдельная команда:

```bash
sudo xm dns-watch 120     # кто на машине шлёт открытый DNS, с атрибуцией
```

Она пассивно слушает заданное окно и показывает каждый источник открытого
запроса с именем-примером. Локальный процесс атрибутируется по UID
(`iptables -j LOG --log-uid`, правило снимается по `trap`), контейнер — по
адресу из docker-сети: у форвардящегося пакета владельца нет вовсе, поэтому
UID ему не приписывается. Это важный отдельный класс: контейнеру Docker
подсовывается внешний резолвер, потому что `127.0.0.53` из его сетевого
namespace недостижим, — и перевод стаба на DoT такие запросы не покрывает.

Если после `xm harden` какое-то приложение начнёт капризничать с DNS — это
`nonIPQuery=drop` (запросы не-A/AAAA отбрасываются вместо пересылки наружу
открытым текстом). Откат: `sudo xm harden --off`.

## Что устанавливается

| Компонент | Назначение |
|---|---|
| **Xray-core** | Прокси-сервер VLESS+REALITY+XHTTP |
| **Nginx** | Настоящий REALITY-fallback: `stream`+`ssl_preread` на `127.0.0.1:10443` прозрачно проксирует TLS-хендшейк на реальный SNI-сайт (не подделка, а честный проброс). Режим mimic: чужой и пустой SNI тоже уходят туда, а не в обрыв |
| **DNS (DoH)** | Xray резолвит домены через DoH и перехватывает `:53` из тоннеля; системный резолвер переведён на DoT, чтобы имя не ушло открытым текстом и в обход Xray. Что из этого реально работает на конкретной сборке — показывает `xm diag-dpi`, тест E5 |
| **fail2ban** | Джейл `sshd` (брутфорс SSH) + `nginx-reality-flood` (бан по объёму соединений, не по факту — легитимные клиенты не задеваются) |
| **chrony** | Точная синхронизация времени (нужна для `maxTimeDiff` REALITY) |
| **UFW** | Файрвол |
| **xm** | Менеджер в `/usr/local/bin/xm` |

Пути:
```
/usr/local/etc/xray/config.json          — конфиг Xray (chmod 640, приватный ключ)
/usr/local/etc/xray/client-info.txt      — данные клиентов (chmod 600)
/usr/local/etc/xray/backups/             — автобэкапы
/var/log/xray/error.log                  — лог Xray
```
