## 2. Ключевой вывод, из которого растёт остальное

REALITY дозванивается до `dest` **на каждое входящее соединение**, а `dest`
в nginx задан именем и резолвится в рантайме. Поэтому:

> сдох резолвинг → nginx не знает апстрим → REALITY некуда форвардить →
> сервер принимает TCP и молча рвёт

А «принял TCP и закрыл» — это подпись прокси, ради ухода от которой сделан
весь mimic-fallback. **Нестабильность здесь равна демаскировке**, это не
две разные темы. Xray при этом жив, systemd ничего не перезапустит —
поэтому проверять надо сквозной путь, а не статус юнитов.

## 4. Снято (проверялось, не подтвердилось)

- BBR отсутствует → включён.
- `LimitNOFILE` мал → 1000000.
- `error_log` в stream течёт IP клиентов → нет, там `client: 127.0.0.1`.
- Xray нестабилен → `NRestarts=0`.
- journald пишет клиентские IP → 0 строк.
- Системный стаб без DoT → `DNSOverTLS setting: yes`, стаб закрыт.
  Именно строгий DoT и объясняет отказы резолвинга: при недоступном `:853`
  резолвед обязан вернуть ошибку, а не уйти в открытый UDP. Это правильное
  поведение; лечится не откатом, а `valid=900s` + watchdog.
- **Сбросы домена-маски как причина мигания на Android** → снято замером
  01.09.2026, см. раздел 3. 16 событий за шесть суток — это раз в сутки;
  мигание раз в пару секунд таким не производится. Домен-маску прошлая
  сессия обвинила напрасно, потому что блок G показывал накопительный
  счётчик без датировки. Это исправлено в коде: вердикт теперь по окну 24 ч,
  плюс строка с давностью последнего отказа.
  Смена домена остаётся осмысленной по другим причинам (раздел 5.3), но
  к этому симптому отношения не имеет.

## 5. Открытые вопросы — с них продолжать

### 5.1. Перенос на TCP/443 (самый крупный оставшийся признак)
Сертификат крупного сайта на нестандартном порту виден сканеру до всякого
анализа TLS. Это единственное «критично» в текущем `diag-dpi` (тест B8).

**Замер 01.09.2026 опроверг предположение прошлой сессии, что TCP/443
свободен: он занят другой службой этого сервера** (B8 показывает, какой
именно). Рассуждение «на 443 только UDP, а это разные сокеты» верно само по
себе, но к фактическому состоянию отношения не имело — проверка делалась
по памяти, а не командой. Перенос заблокирован, пока владелец не решит, что
делать с занявшей порт службой.
```bash
sudo ss -tlnp | awk '$4 ~ /:443$/'   # сейчас НЕ пусто
sudo xm set-port 443 && sudo xm qr --all
```

### 5.2. Мигание «соединение» в мессенджере на Android
Версия про сбросы домена-маски **снята** (раздел 4). Осталось три кандидата,
в порядке правдоподобия:

1. **Сетевой стек не настроен — `xm tune` не применялся.** Единственный
   кандидат, объясняющий, почему симптом только на Android: `tcp_mtu_probing=0`
   плюс мобильная сеть даёт PMTU blackhole. Оператор режет MTU и глушит ICMP
   Too Big, полноразмерные пакеты пропадают молча, ядро ретранслирует до
   разрыва — «работает → виснет → отвисает». Windows и macOS сидят на 1500
   и этого не видят. Косвенно подтверждается 6.16% ретрансмитов при уже
   включённом BBR: алгоритм ни при чём, это потери или MTU.
2. **Очередь accept переполняется** — overflows 813, drops 1193. Подключения
   теряются молча ещё до Xray. Лечится тем же `xm tune` (`somaxconn`,
   `tcp_max_syn_backlog`).
3. **`nonIPQuery: drop`** — в живом конфиге присутствует, сборка 26.3.27 его
   приняла. Android с 11-й версии сам запрашивает HTTPS/SVCB (тип 65).
   Проверять **после** первых двух: те дешевле, обратимы одной командой и
   не трогают приватность. Набор допустимых значений сверять с фактической
   сборкой (`xray -test` на копии конфига), не гадать.

Порядок: `sudo xm tune` → сутки пользования → `sudo xm diag-dpi` и смотреть
строку дельты, а не накопительные проценты. Если не помогло — `xm harden --off`
на 10–15 мин как тест кандидата 3.

Разделитель по транспорту: переключить телефон на второй inbound
(`xm qr --tcp`). Осторожно с направлением вывода — TCP/Vision открывает
**больше** дозвонов до `dest`, чем XHTTP с мультиплексированием, по одному
на каждое проксируемое соединение. Значит «на TCP стало хуже» указывает на
`dest`, а «на TCP стало лучше» — на XHTTP и переработку соединений.

### 5.2a. `sniffing` без `routeOnly`
На обоих inbound `sniffing.enabled: true` с `destOverride`, `routeOnly` не
задан. Без него найденный домен **заменяет адрес назначения**, и сервер
обязан резолвить его сам — лишний DNS-раунд на каждое соединение там, где
резолвинг уже признан хрупким. `routeOnly: true` оставляет правилам
маршрутизации имя, а соединению — исходный адрес. Не проверено, что это
влияет на симптом; правка сама по себе разумная, но отдельная.

### 5.3. Смена домена-маски
Текущий периодически сбрасывает соединения с этого VPS, и сам по себе
популярен как REALITY-dest. Подбор по факту: `sudo xm sni-scan`. Критерии:
TLS 1.3 + ALPN h2 обязательны, компактный сертификат (лимит буфера REALITY
~8192 б), низкий RTT, **и** правдоподобность присутствия на IP этого хостера.

## 7. Правила работы по этому проекту

- Отвечать по-русски. Активировать скилл `xray-dpi` (`.claude/skills/xray-dpi/`).
- Сначала команды проверки → дождаться результатов → только потом код.
  После правок — команды, которыми владелец убедится в эффекте.
- Минимум изменений в существующие файлы, без дублирования.
- Команды, требующие прав, писать с `sudo`.
- `setup.sh` идёт под `set -euo pipefail`: `grep` без совпадения возвращает 1
  и роняет конвейер. `xm.sh` под `set -e` **не** идёт — поведение разное.
- Сторонние сервисы владельца (что ещё живёт на VPS) в коде, README и
  коммитах не упоминать. Формулировать нейтрально: «служба на UDP с тем же
  номером».
- Никаких IP, UUID, ключей и имён хостера в коммитах.
