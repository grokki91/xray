# Хендофф: с чего продолжать

Только то, с чего продолжать работу: открытые вопросы, снятые гипотезы, долг — до 150 строк.
Сделанное — в `git log` и PR; закрытое отсюда удаляется, общий вывод из него — в
`xray-dpi/references/lessons.md`. Идентификаторов установки здесь нет (IP, хостер, UUID,
порты, выдержки из логов): репозиторий публичный, детали сервера — в `sudo xm journal` на VPS.

## 1. Ключевой вывод

REALITY дозванивается до `dest` **на каждое входящее соединение**, а `dest` в nginx задан
именем и резолвится в рантайме:

> сдох резолвинг → nginx не знает апстрим → REALITY некуда форвардить →
> сервер принимает TCP и молча рвёт

«Принял TCP и закрыл» — подпись прокси, ради ухода от которой сделан весь mimic-fallback.
**Нестабильность здесь равна демаскировке.** Xray при этом жив, systemd ничего не перезапустит —
проверять сквозной путь, а не статус юнитов.

Что ещё учитывать в замерах:

- строки старого strict-режима (`no host in upstream`) отфильтровывать — иначе они маскируют
  реальную картину отказов;
- холодный резолвинг `dest` — единицы секунд, тёплый — миллисекунды: с `policy.handshake: 4`
  клиент, попавший в холодный кэш, не входит в окно.

## 2. Снято (проверялось, не подтвердилось)

- BBR отсутствует → включён.
- `LimitNOFILE` у юнита Xray мал → поднят официальным установщиком (у nginx — отдельная
  величина, поднята `_ngx_rlimit_nofile`).
- `error_log` в stream течёт IP клиентов → нет, там `client: 127.0.0.1`.
- Xray нестабилен → рестартов нет. journald пишет клиентские IP → не пишет.
- Системный стаб без DoT → DoT строгий, стаб закрыт. Отказы резолвинга при недоступном `:853` —
  правильное поведение строгого DoT; лечится `valid=900s` + watchdog, а не откатом.
- Сбросы домена-маски как причина мигания на Android → событий порядка одного в сутки, а
  симптом — раз в пару секунд.
- `sniffing` без `routeOnly` → менять не надо: адрес почти всегда в кэше (`disableCache: false`,
  клиент получил его от нашего DoH), а `destOverride` защищает от адреса, подменённого
  резолвером провайдера. Возвращаться, только если замер покажет резолвинг на каждое соединение.
- «Хостер режет `:853`» → нет: причиной был сломанный детектор DoT (урок «Детектор состояния
  разбирал человекочитаемый вывод»); с 22.09.2026 строгий DoT с четырьмя апстримами.

## 3. Открытые вопросы — с них продолжать

### 3.1. Не проверено на боевом сервере

Ветки `loving-wozniak` и `serene-heisenberg` проверены статически и в песочнице. Прогон PR #29
на живом VPS был (по нему в #29 влит #27), но эффекты ниже там не записаны — сверить при
следующем прогоне `xm self-update`, `xm sni-scan`, `xm diag-dpi`:

- `self-update` ищет установленный файл по хешу среди версий `xm.sh` во всех ветках:
  нашёлся — называет коммит, нет — «правили на сервере»;
- `sni-scan` резолвит имя один раз и мерит пробы на адрес; порог ML-DSA — из исходника REALITY;
- geoip:ru из тоннеля → blackhole (`xm harden`, `--ru on|off`, новые установки — setup.sh),
  `diag-dpi` блок H через `_ru_probe`;
- порог сертификата маски по версии Xray (`_cert_limits`); `xray-sni-watch` на уже
  установленных серверах держит старый порог (его ставит setup.sh, self-update не трогает) —
  `xm info` сверяет размер из флага с порогом версии;
- `diag-dpi` G5 — шторм соединений с одного адреса и отказы `limit_conn` фронта за сутки.

### 3.2. Мигание «соединение» в мессенджере на Android

Сняты замером: не применённый `xm tune`, переполнение accept-очереди. Доля ретрансмитов в окне
остаётся высокой — выше накопительной, то есть потери идут сейчас; BBR и fq включены, значит
это последняя миля у клиентов или участок пути от VPS.

- **Кандидат 3 — режим запросов не-A/AAAA.** Android с 11-й версии запрашивает HTTPS/SVCB
  (тип 65); `drop` молчит, и клиент ждёт таймаут. С 22.09.2026 на сервере `reject` (`diag-dpi`
  E4b зелёный), но эффект на мигание не измерен: нужны 10–15 минут реального пользования
  телефоном. Замер 22.09.2026 сделан при `drop` — годится как точка «до». Сравнивать
  `drop` ↔ `reject`; `skip` для этой гипотезы больше не нужен.
- **Сосед по симптому:** за сутки несколько отказов fallback, где сам домен-маска сбросил или
  не ответил. Бьёт по частым новым соединениям и к DNS отношения не имеет — держать отдельным
  кандидатом.
- **Кандидат 4:** ядро Xray в клиенте v26.9.8+ (XTLS/Xray-core#6797) при зависших хендшейках
  плодит соединения, ТСПУ отвечает заморозкой. Видно в `diag-dpi` G5; проверить версию ядра в
  приложении. Симптом скорее «пропадает на минуты», чем «мигает раз в пару секунд».

Разделитель по транспорту — переключить телефон на второй inbound (`xm qr --tcp`). TCP/Vision
открывает **больше** дозвонов до `dest`, чем XHTTP с мультиплексом: «на TCP хуже» указывает на
`dest`, «на TCP лучше» — на XHTTP.

### 3.3. Смена домена-маски

По `xm sni-scan` текущий домен выигрывал у кандидатов по размеру сертификата и по RTT, но
колонка RTT тогда включала резолв имени (урок «Замер пути включал резолв имени») — **сравнение
по RTT пересобрать** новым `sni-scan`.

Нетехнический довод: это самый растиражированный REALITY-dest, и «адрес с его сертификатом не
из его сети» — дешёвая эвристика для перечисления. Признак снимает только сосед по своей сети
(`sni-scan --local`) или self-steal. Решение владельца; критерии: TLS 1.3 + ALPN h2, сертификат
с запасом до буфера REALITY (и не меньше ~3.5 КБ, если нужен ML-DSA), низкий RTT.

### 3.4. `nonIPQuery` устарел — переезд на `settings.rules`

Xray печатает, что `nonIPQuery` и `blockTypes` dns-outbound уходят в `settings.rules`; на
v26.9.30 оба поля ещё принимаются. Проверено на живом бинаре:

```json
"settings": { "rules": [
  { "action": "hijack", "qType": "1,28" },
  { "action": "return", "rCode": 0 }
] }
```

`qType` — строка вида списка портов; массив `[1,28]` не парсится (`invalid port`). На тип 65 —
NOERROR с пустым ответом (NODATA): клиент его кэширует, а REFUSED может заставить перебирать
другие резолверы.

Не сделано, потому что `xm harden --nonip` читает и пишет `nonIPQuery`, а смешивать его с
`rules` сборка запрещает. Переезд — разом `_nonip_current`, `_nonip_patch` и вывод состояния:
цепочка `rules → reject → drop → без поля`, `_nonip_current` возвращает режим из любой формы.
Иначе диагностика скажет «поле не задано» на конфиге, где режим задан. Если `nonIPQuery`
уберут совсем, деградация ведёт к ответу, а не к молчанию: без правил A/AAAA идут в перехват,
остальное получает NOERROR (по исходникам dns-outbound).

### 3.5. Расхождения кода с актуальной картиной (10.2026)

Решать по одному, каждое со своей проверкой на VPS:

- **Маска по умолчанию — глобальные CDN.** Несовпадение SNI и сети сервера — главный признак с
  17.02.2026; `sni-scan --local` снимает его только на уровне ASN. Режима self-steal нет;
  решение владельца — домен связывает его с сервером.
- **Клиентская сторона не описана в выдаче.** В client-info и QR нет раздельной маршрутизации
  российских адресов, предупреждения о локальном SOCKS (2026-04) и запасного `fp=firefox` для
  операторов, где режут chrome.
- **`dest` — устаревшее имя `target`** (принимается). Переименование — четыре jq-пути
  `realitySettings.dest` в xm.sh.

## 4. Долг

В 2026-09 история переписана `git filter-repo` (реальный IP из комментария `setup.sh`); в
ветках на GitHub совпадений нет. **Остаётся:** `refs/pull/5/head` — два коммита несут реальный
маршрутизируемый адрес в примере `xm unban` в README. Страницы закрытых PR хранят диффы и
переживают force-push: убрать можно только тикетом в GitHub Support, назвав PR #5. Проверять
шаблоном из `AGENTS.md` по `git rev-list refs/pull/N/head`, а не по рабочему дереву.

Клон со старой историей (локальная машина, VPS) не сделает `git pull` («diverged»): после
проверки `git status` — `git fetch origin main && git checkout main && git reset --hard origin/main`.
