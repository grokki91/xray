# Хендофф: аудит DPI / деанонимизации / стабильности

Рабочий документ для продолжения в новой сессии.

**В этом файле намеренно нет ни одного идентификатора конкретной установки** —
ни IP, ни хостера, ни UUID, ни фактических портов, ни счётчиков и выдержек из
логов боевого сервера. Репозиторий публичный, и профиль установки, собранный
из таких мелочей, сам по себе является утечкой. Владелец сообщает эти значения
в чате; в коммиты они не попадают. Правила — в `.claude/skills/xray-dpi/SKILL.md`.

### Ветка `claude/dpi-protection-review-xfnyvq`

Ревизия по коду, три дефекта и одна ручка:

- **`xm front on` не открывал публичный порт в UFW.** Установка открывает порт
  inbound, фронт слушает публичный — это разные номера. Сокет поднимался,
  `front status` показывал «порт держит nginx», `diag-dpi` был зелёным, а
  снаружи не подключался никто. Добавлены `_ufw_active/_ufw_allowed/_ufw_open`,
  правило ставится в `front on`; `front off` возвращает правило порту inbound.
- **`diag-dpi` не мог этого заметить в принципе.** Зонды идут с самого VPS на
  его же внешний адрес, то есть через `lo`, а петлю ufw пропускает целиком
  (`-i lo -j ACCEPT`). Закрытый снаружи порт выглядел безупречно. В B8
  добавлена отдельная проверка правила ufw для публичного порта.
- **`worker_connections 4096` без `worker_rlimit_nofile`.** Соединение — это
  дескриптор, а больше выданного systemd (1024 по умолчанию) воркер открыть не
  может: nginx пишет одну строку при старте и дальше молча не принимает лишние
  соединения. Молча потерянное соединение здесь равно «принял TCP и закрыл».
  Добавлен `_ngx_rlimit_nofile` (16384, с бэкапом, `nginx -t` и откатом).
- **`xm harden --nonip [drop|skip|off]`** — точечная смена режима запросов
  не-A/AAAA. Раньше проверить гипотезу 5.2.3 можно было только через
  `harden --off`, который заодно снимает DoH, перехват :53, строгий DoT и
  mimic. Допустимые значения не хардкожены: каждое проверяется `xray -test` на
  копии конфига.

## 2. Ключевой вывод, из которого растёт остальное

REALITY дозванивается до `dest` **на каждое входящее соединение**, а `dest` в
nginx задан именем и резолвится в рантайме. Поэтому:

> сдох резолвинг → nginx не знает апстрим → REALITY некуда форвардить →
> сервер принимает TCP и молча рвёт

А «принял TCP и закрыл» — это подпись прокси, ради ухода от которой сделан
весь mimic-fallback. **Нестабильность здесь равна демаскировке**, это не две
разные темы. Xray при этом жив, systemd ничего не перезапустит — поэтому
проверять надо сквозной путь, а не статус юнитов.

## 3. Методические выводы из замеров

Конкретные числа остаются в чате; сюда вынесено только то, что меняет код:

- **Накопительный счётчик без датировки читается как текущее состояние.**
  Именно так прошлая сессия сделала сброс домена-маски ведущей гипотезой:
  блок G показывал итог за всё время жизни файла. Исправлено — вердикт по
  окну 24 ч плюс давность последнего реального отказа. То же для счётчиков
  ядра: добавлена точка отсчёта в `/var/lib`, вывод дельты, `xm tune` ставит
  точку заново.
- **Строки старого strict-режима (`no host in upstream`) надо отфильтровывать**,
  иначе они маскируют реальную картину отказов.
- **Холодный резолвинг `dest` занимает единицы секунд, тёплый — миллисекунды.**
  С `policy.handshake: 4` клиент, попавший в холодный кэш, не входит в окно.
- **Проверять командой, а не по памяти.** Предположение прошлой сессии, что
  TCP/443 свободен, оказалось неверным — порт занят другой службой. Само
  рассуждение «TCP и UDP на одном номере не конфликтуют» верно, но к
  фактическому состоянию отношения не имело.

## 4. Снято (проверялось, не подтвердилось)

- BBR отсутствует → включён.
- `LimitNOFILE` у юнита Xray мал → уже поднят официальным установщиком.
  У nginx это отдельная величина и она поднята не была — см. §1.
- `error_log` в stream течёт IP клиентов → нет, там `client: 127.0.0.1`.
- Xray нестабилен → рестартов нет.
- journald пишет клиентские IP → не пишет.
- Системный стаб без DoT → DoT включён, стаб закрыт. Именно строгий DoT и
  объясняет отказы резолвинга: при недоступном `:853` резолвед обязан вернуть
  ошибку, а не уйти в открытый UDP. Это правильное поведение; лечится не
  откатом, а `valid=900s` + watchdog.
- **Сбросы домена-маски как причина мигания на Android** → снято: событий
  порядка одного в сутки, а симптом — раз в пару секунд. Смена домена
  остаётся осмысленной по другим причинам (5.3), но к этому симптому
  отношения не имеет.

## 5. Открытые вопросы — с них продолжать

### 5.1. Выход на TCP/443
Сертификат крупного сайта на нестандартном порту виден сканеру до всякого
анализа TLS — единственное «критично» в текущем `diag-dpi` (тест B8).
Технически больше не заблокировано: `xm front` делит публичный порт по SNI,
соседняя служба остаётся на месте. Осталось действие владельца.

```bash
sudo ss -tlnp | awk '$4 ~ /:443$/'     # кто держит TCP/443 сейчас
# если TCP/443 свободен:
sudo xm set-port 443 && sudo xm qr --all
# если занят соседом, который умеет переехать на loopback:
sudo xm front add <SNI соседа> <его локальный порт>
sudo xm front on && sudo xm qr --all
```

Порядок после включения фронта: раздать новые URI → `xm selftest` →
`xm diag-dpi` (B8) → и только потом закрывать старый порт в ufw.

### 5.2. Мигание «соединение» в мессенджере на Android
Три кандидата в порядке правдоподобия:

1. **`xm tune` не применялся.** Единственный кандидат, объясняющий, почему
   симптом только на Android: `tcp_mtu_probing=0` плюс мобильная сеть даёт
   PMTU blackhole. Оператор режет MTU и глушит ICMP Too Big, полноразмерные
   пакеты пропадают молча, ядро ретранслирует до разрыва. Windows и macOS
   сидят на 1500 и этого не видят.
2. **Очередь accept переполняется** — подключения теряются молча ещё до Xray.
   Лечится тем же `xm tune` (`somaxconn`, `tcp_max_syn_backlog`).
3. **`nonIPQuery: drop`** — Android с 11-й версии сам запрашивает HTTPS/SVCB
   (тип 65). Проверять **после** первых двух: те дешевле, обратимы одной
   командой и не трогают приватность.

Порядок: `sudo xm tune` → сутки пользования → `sudo xm diag-dpi` и смотреть
строку дельты, а не накопительные проценты. Если не помогло — кандидат 3
проверяется точечно, без отката всего harden:

```bash
sudo xm harden --nonip          # что принимает эта сборка Xray
sudo xm harden --nonip skip     # 10-15 мин пользования
sudo xm harden --nonip drop     # вернуть в любом случае
```

`skip` — режим на время проверки: запросы не-A/AAAA уходят с VPS открытым UDP.
Если мигание уходит именно на нём — виноват кандидат 3, и дальше надо искать
режим мягче `drop`, но без открытого UDP, а не оставлять `skip`.

Разделитель по транспорту: переключить телефон на второй inbound
(`xm qr --tcp`). Осторожно с направлением вывода — TCP/Vision открывает
**больше** дозвонов до `dest`, чем XHTTP с мультиплексированием. Значит
«на TCP стало хуже» указывает на `dest`, а «на TCP стало лучше» — на XHTTP.

### 5.2a. `sniffing` без `routeOnly` — закрыто решением, кода не будет
На обоих inbound `sniffing.enabled: true` с `destOverride` и без `routeOnly`,
то есть найденный домен заменяет адрес назначения и сервер резолвит его сам.
Разбор показал, что менять это не надо:

- лишнего раунда почти нет: `dns.disableCache: false`, а адрес в подавляющем
  большинстве случаев уже в кэше — клиент получил его от нашего же DoH через
  перехват :53;
- `destOverride` здесь ещё и защита: клиент, у которого DNS идёт мимо тоннеля,
  приносит адрес от резолвера провайдера, то есть потенциально подменённый.
  Пересоздание адреса по имени на сервере это отменяет, `routeOnly: true` —
  наоборот, заставило бы идти по клиентскому адресу.

Возвращаться сюда стоит, только если замер покажет, что резолвинг реально
происходит на каждое соединение (то есть кэш не работает).

### 5.3. Смена домена-маски
Подбор по факту: `sudo xm sni-scan`. Критерии: TLS 1.3 + ALPN h2 обязательны,
компактный сертификат (лимит буфера REALITY ~8192 б), низкий RTT, **и**
правдоподобность присутствия на IP этого хостера.

`git pull` там не сработает («diverged»). Нужно:
```bash
git fetch origin main && git checkout main && git reset --hard origin/main
```
Проверить `git status` до этого — `reset --hard` затирает незакоммиченное.

## 7. Правила работы по этому проекту

- Отвечать по-русски. Активировать скилл `xray-dpi` (`.claude/skills/xray-dpi/`).
- Сначала команды проверки → дождаться результатов → только потом код.
  После правок — команды, которыми владелец убедится в эффекте.
- Минимум изменений в существующие файлы, без дублирования.
- Команды, требующие прав, писать с `sudo`.
- `setup.sh` идёт под `set -euo pipefail`: `grep` без совпадения возвращает 1
  и роняет конвейер. `xm.sh` под `set -e` **не** идёт — поведение разное.
- Никаких идентификаторов установки в коде, README, коммитах и PR — полный
  список и порядок проверки в скилле `xray-dpi`.
