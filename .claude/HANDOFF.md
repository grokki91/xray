## 2. Ключевой вывод, из которого растёт остальное

REALITY дозванивается до `dest` **на каждое входящее соединение**, а `dest` в
nginx задан именем и резолвится в рантайме. Поэтому:

> сдох резолвинг → nginx не знает апстрим → REALITY некуда форвардить →
> сервер принимает TCP и молча рвёт

А «принял TCP и закрыл» — это подпись прокси, ради ухода от которой сделан
весь mimic-fallback. **Нестабильность здесь равна демаскировке**, это не две
разные темы. Xray при этом жив, systemd ничего не перезапустит — поэтому
проверять надо сквозной путь, а не статус юнитов.

## 3. Методические выводы из замеров

Конкретные числа остаются в чате; сюда вынесено только то, что меняет код:

- **Накопительный счётчик без датировки читается как текущее состояние.**
  Именно так прошлая сессия сделала сброс домена-маски ведущей гипотезой:
  блок G показывал итог за всё время жизни файла. Исправлено — вердикт по
  окну 24 ч плюс давность последнего реального отказа. То же для счётчиков
  ядра: добавлена точка отсчёта в `/var/lib`, вывод дельты, `xm tune` ставит
  точку заново.
- **Строки старого strict-режима (`no host in upstream`) надо отфильтровывать**,
  иначе они маскируют реальную картину отказов.
- **Холодный резолвинг `dest` занимает единицы секунд, тёплый — миллисекунды.**
  С `policy.handshake: 4` клиент, попавший в холодный кэш, не входит в окно.
- **Проверять командой, а не по памяти.** Предположение прошлой сессии, что
  TCP/443 свободен, оказалось неверным — порт занят другой службой. Само
  рассуждение «TCP и UDP на одном номере не конфликтуют» верно, но к
  фактическому состоянию отношения не имело.
- **Снимок `ss` не отвечает на вопрос «пользуются ли службой».** Ноль
  установленных соединений — состояние на одну секунду, а не факт простоя.
  Признак использования — накопительный счётчик трафика (`docker stats`
  Net I/O для контейнера, счётчики интерфейса для службы). Симметричные
  «вошло ≈ вышло» сотни мегабайт означают живой прокси; сканы и боты дают
  килобайты. На этой ошибке едва не был снесён используемый канал.
- **Docker публикует порты мимо UFW.** Правила пишутся в свои цепочки
  iptables, поэтому `ufw status` не показывает опубликованные контейнерами
  порты, а они при этом открыты наружу. Вывод `ufw status` — неполная
  картина доступного снаружи; сверять с `ss -tlnp` / `ss -ulnp`.

## 4. Снято (проверялось, не подтвердилось)

- BBR отсутствует → включён.
- `LimitNOFILE` мал → поднят.
- `error_log` в stream течёт IP клиентов → нет, там `client: 127.0.0.1`.
- Xray нестабилен → рестартов нет.
- journald пишет клиентские IP → не пишет.
- Системный стаб без DoT → DoT включён, стаб закрыт. Именно строгий DoT и
  объясняет отказы резолвинга: при недоступном `:853` резолвед обязан вернуть
  ошибку, а не уйти в открытый UDP. Это правильное поведение; лечится не
  откатом, а `valid=900s` + watchdog.
- **Watchdog не работает** → ложная тревога. `xm neighbors` показывает
  `xray-watchdog.service` как `inactive`, но это oneshot, запускаемый
  таймером: между срабатываниями `inactive` — норма. Смотреть надо
  `xm watchdog status` (состояние таймера), а не юнита. Таймер активен,
  вмешательств за неделю не потребовалось.
- **Сбросы домена-маски как причина мигания на Android** → снято: событий
  порядка одного в сутки, а симптом — раз в пару секунд. Смена домена
  остаётся осмысленной по другим причинам (5.3), но к этому симптому
  отношения не имеет.

## 5. Открытые вопросы — с них продолжать

### 5.1. Перенос на TCP/443 — заблокирован, решение за владельцем

Сертификат крупного сайта на нестандартном порту виден сканеру до всякого
анализа TLS — единственное «критично» в текущем `diag-dpi` (тест B8).

**Кто занимает порт (выяснено 01.09.2026).** Не то, что предполагалось.
Стороннее VPN-приложение владельца развернуло на этой же машине в Docker
**второй Xray**, и он занял TCP/443. Плюс его же WireGuard-контейнер на UDP
с другим номером — этот не конфликтует ни с чем и помехой не является.
Итого на VPS два независимых Xray: наш (`/opt/xray` → `/usr/local/bin/xray`,
управляется `xm`) и чужой в контейнере (управляется своим приложением).
Отсюда же росла исходная путаница владельца «какой xray у меня рабочий».

Первая гипотеза была «порт занял WireGuard» — неверна: WireGuard работает
только по UDP и TCP-порт занять не может в принципе. Проверять `docker ps`,
а не додумывать по названиям контейнеров.

**Контейнер используется.** Трафик за время работы — сотни мегабайт,
симметрично по обоим направлениям. Мало, но это не простой (см. 3, про
снимок `ss`). Поэтому снос вслепую исключён.

**Три пути, выбор за владельцем:**

- **A. Оставить наш, чужой убрать.** Наш функционально богаче: REALITY+XHTTP
  с fallback на настоящий сайт, DoH и перехват `:53`, watchdog, `harden`,
  весь блок диагностики. Порядок обязателен: сперва перевести все клиенты на
  наш Xray и убедиться, что работает, и только потом удалять. Удалять —
  **через приложение, а не `docker rm`**: иначе приложение считает протокол
  установленным и может пересоздать контейнер поверх занятого порта.
  WireGuard-контейнер при этом стоит оставить: другой протокол, полезен как
  резерв, если DPI прижмёт TLS-транспорт.
- **B. Оставить оба, наш живёт на текущем порту.** То, что есть сейчас.
  Мирится с порт-аномалией; два прокси на машине конкурируют за один и тот
  же приём маскировки.
- **C. Разделение по SNI на 443.** nginx stream с `ssl_preread` встаёт на
  `0.0.0.0:443` и разводит: SNI домена-маски → наш Xray, остальное → чужой
  контейнер. Половина механизма уже есть (`reality-fallback.conf`). Минусы:
  `xm` схему не знает, `setup.sh --reinstall` её снесёт, и надо аккуратно с
  `proxy_protocol` — наш inbound ждёт `xver=2`. Владелец про этот вариант
  спрашивал отдельно; расписывать по запросу.

После освобождения порта:
```bash
sudo ss -tlnp | awk 'NR>1 && $4 ~ /:443$/'   # должно быть пусто
sudo xm set-port 443 && sudo xm qr --all     # порт зашит в URI, старые умрут
sudo xm selftest
```
`xm set-port` проверяет занятость только по TCP и сам сообщает, если на том
же номере есть UDP-служба — это уже учтено, отдельной правки не требует.

### 5.1a. UFW разросся
Наблюдение из `xm neighbors`, разбирать после 5.1, чтобы не чистить дважды.
Есть правило для стандартного SSH-порта, открытое всему интернету, хотя SSH
давно переехал; правило для 443 без указания протокола; `Nginx Full`,
дублирующий отдельное правило для `:80`; правило под UDP-порт прошлой
установки WireGuard, которая теперь слушает другой номер. Правило SSH трогать
последним и обязательно имея открытую вторую сессию.

### 5.2. Мигание «соединение» в мессенджере на Android
Три кандидата в порядке правдоподобия:

1. **`xm tune` не применялся.** Единственный кандидат, объясняющий, почему
   симптом только на Android: `tcp_mtu_probing=0` плюс мобильная сеть даёт
   PMTU blackhole. Оператор режет MTU и глушит ICMP Too Big, полноразмерные
   пакеты пропадают молча, ядро ретранслирует до разрыва. Windows и macOS
   сидят на 1500 и этого не видят.
2. **Очередь accept переполняется** — подключения теряются молча ещё до Xray.
   Лечится тем же `xm tune` (`somaxconn`, `tcp_max_syn_backlog`).
3. **`nonIPQuery: drop`** — Android с 11-й версии сам запрашивает HTTPS/SVCB
   (тип 65). Проверять **после** первых двух: те дешевле, обратимы одной
   командой и не трогают приватность. Набор допустимых значений сверять с
   фактической сборкой (`xray -test` на копии конфига), не гадать.

Порядок: `sudo xm tune` → сутки пользования → `sudo xm diag-dpi` и смотреть
строку дельты, а не накопительные проценты. Если не помогло — `xm harden --off`
на 10–15 мин как тест кандидата 3.

Разделитель по транспорту: переключить телефон на второй inbound
(`xm qr --tcp`). Осторожно с направлением вывода — TCP/Vision открывает
**больше** дозвонов до `dest`, чем XHTTP с мультиплексированием. Значит
«на TCP стало хуже» указывает на `dest`, а «на TCP стало лучше» — на XHTTP.

### 5.2a. `sniffing` без `routeOnly`
На обоих inbound `sniffing.enabled: true` с `destOverride`, `routeOnly` не
задан. Без него найденный домен **заменяет адрес назначения**, и сервер обязан
резолвить его сам — лишний DNS-раунд на каждое соединение там, где резолвинг
уже признан хрупким. `routeOnly: true` оставляет правилам маршрутизации имя, а
соединению — исходный адрес. Правка разумная, но отдельная: связь с симптомом
не проверена.

### 5.3. Смена домена-маски
Подбор по факту: `sudo xm sni-scan`. Критерии: TLS 1.3 + ALPN h2 обязательны,
компактный сертификат (лимит буфера REALITY ~8192 б), низкий RTT, **и**
правдоподобность присутствия на IP этого хостера.

### 5.4. Дубликаты чекаутов на VPS — закрыто 01.09.2026

Владелец не мог понять, какой Xray у него рабочий: копии исходников были
разбросаны по домашнему каталогу, включая вложенный чекаут времён до
переименования `script.sh` → `setup.sh` (отставал на полсотни коммитов) и
отдельные копии `xm.sh` / `setup.sh` версий на два минора старше.

Разобрано. Канонический чекаут — `/opt/xray`, на него указывает
`/usr/local/etc/xray/xm-source`, установленный `xm` из него же. Всё
остальное из домашнего каталога удалено; ни одна из копий уникальных правок
не содержала (сверено md5 каждой копии со всеми историческими версиями файла
в git — совпадений с рабочей версией нет, значит это просто старые релизы).

Что стоит помнить:

- **Ни одна папка с исходниками не является «работающим сервером».** Сервер —
  это `/usr/local/bin/xray` + `/usr/local/etc/xray/config.json` + юнит.
  Чекаут нужен ровно для одного: `xm self-update` берёт из него `xm.sh`.
  Удаление любого чекаута сервер не трогает.
- **Лишний чекаут в домашнем каталоге опасен.** Потеряется `xm-source` —
  и `_xm_repo` пойдёт перебором по `/opt/xray`, `/root/xray`, `/home/*/xray`
  и может молча взять чужую старую копию. Держать чекаут только в `/opt/xray`.
- Перед удалением любой копии — `git -C <путь> status --short` и сверка md5
  с рабочей версией. `setup.sh` запускать только на первой установке.

### 5.5. Ретрансмиты и разрывы — новый открытый вопрос

`xm tune --check` даёт по последнему окну долю ретрансмитов на порядок выше
нормы при уже включённом BBR. Накопительные счётчики переполнения accept-
очереди и потерь UDP при этом за окно чистые — узкое место не в приёме
соединений. В ту же сторону указывает оборвавшаяся SSH-сессия
(`client_loop: send disconnect: Connection reset`), хотя одиночный разрыв сам
по себе может быть и домашней сетью владельца.

Начинать с разделения: проблема на стороне VPS или на пути от владельца до
него. Лечится это по-разному, и до разделения менять sysctl бессмысленно.
Браться после 5.1 — не менять две вещи разом, иначе непонятно, что подействовало.

## 6. Долг

Закрыт 01.09.2026. В `fcbd0c1` в комментарий `setup.sh` попал реальный IP
боевого сервера; из файла убран в `7ceed07`, но оставался в истории трёх
веток (`main` и два уже смерженных PR). История переписана `git filter-repo`
(замена IP на документационный адрес во всех блобах), проверена свежим
клоном — совпадений не осталось ни в одной ветке на GitHub. SHA всех
коммитов от `fcbd0c1` и позже изменились.

**Остаточный след, который не закрывается перезаписью:** страницы уже
закрытых PR #2 и #5 на GitHub хранят диффы по внутренним `refs/pull/N/head`
независимо от состояния веток и переживают force-push. Убрать можно только
через тикет в GitHub Support.

**Если где-то ещё лежит клон со старой историей** (локальная машина, VPS) —
`git pull` там не сработает («diverged»). Нужно:
```bash
git fetch origin main && git checkout main && git reset --hard origin/main
```
Проверить `git status` до этого — `reset --hard` затирает незакоммиченное.

## 7. Правила работы по этому проекту

- Отвечать по-русски. Активировать скилл `xray-dpi` (`.claude/skills/xray-dpi/`).
- Сначала команды проверки → дождаться результатов → только потом код.
  После правок — команды, которыми владелец убедится в эффекте.
- Минимум изменений в существующие файлы, без дублирования.
- Команды, требующие прав, писать с `sudo`.
- `setup.sh` идёт под `set -euo pipefail`: `grep` без совпадения возвращает 1
  и роняет конвейер. `xm.sh` под `set -e` **не** идёт — поведение разное.
- Никаких идентификаторов установки в коде, README, коммитах и PR — полный
  список и порядок проверки в скилле `xray-dpi`.
