# Хендофф: аудит DPI / деанонимизации / стабильности

Рабочий документ для продолжения в новой сессии.

**В этом файле намеренно нет ни одного идентификатора конкретной установки** —
ни IP, ни хостера, ни UUID, ни фактических портов, ни счётчиков и выдержек из
логов боевого сервера. Репозиторий публичный, и профиль установки, собранный
из таких мелочей, сам по себе является утечкой. Владелец сообщает эти значения
в чате; в коммиты они не попадают. Правила — в `.claude/skills/xray-dpi/SKILL.md`.

### Ветка `claude/dpi-protection-review-xfnyvq`

Ревизия по коду, три дефекта и одна ручка:

- **`xm front on` не открывал публичный порт в UFW.** Установка открывает порт
  inbound, фронт слушает публичный — это разные номера. Сокет поднимался,
  `front status` показывал «порт держит nginx», `diag-dpi` был зелёным, а
  снаружи не подключался никто. Добавлены `_ufw_active/_ufw_allowed/_ufw_open`,
  правило ставится в `front on`; `front off` возвращает правило порту inbound.
- **`diag-dpi` не мог этого заметить в принципе.** Зонды идут с самого VPS на
  его же внешний адрес, то есть через `lo`, а петлю ufw пропускает целиком
  (`-i lo -j ACCEPT`). Закрытый снаружи порт выглядел безупречно. В B8
  добавлена отдельная проверка правила ufw для публичного порта.
- **`worker_connections 4096` без `worker_rlimit_nofile`.** Соединение — это
  дескриптор, а больше выданного systemd (1024 по умолчанию) воркер открыть не
  может: nginx пишет одну строку при старте и дальше молча не принимает лишние
  соединения. Молча потерянное соединение здесь равно «принял TCP и закрыл».
  Добавлен `_ngx_rlimit_nofile` (16384, с бэкапом, `nginx -t` и откатом).
- **`xm harden --nonip [drop|skip|off]`** — точечная смена режима запросов
  не-A/AAAA. Раньше проверить гипотезу 5.2.3 можно было только через
  `harden --off`, который заодно снимает DoH, перехват :53, строгий DoT и
  mimic. Допустимые значения не хардкожены: каждое проверяется `xray -test` на
  копии конфига.

Второй заход, уже по фактическим замерам с сервера:

- **Модуль headers-more не ставился, только советовался.** Без него заголовок
  `Server` на `:80` поменять нечем (`server_tokens off` убирает лишь версию), и
  тест B7 оставался красным сколько угодно долго. Теперь `xm harden` ставит
  пакет и перезапускает nginx (новый динамический модуль по reload не
  подхватывается), а `diag-dpi` в B7 называет причину, а не только симптом.
- **Drop-in systemd-resolved не обновлялся никогда.** Условие шага было «DoT
  включён → не трогаю», поэтому любая правка списка апстримов не доезжала до
  уже настроенного сервера. Теперь сравнение по содержимому: наш файл
  обновляется, чужая конфигурация DoT по-прежнему не трогается. Апстримов
  четыре вместо двух — под строгим DoT недоступность одного провайдера даёт
  SERVFAIL, а это мёртвый резолвинг `dest` и подпись прокси на всё время.
- **Вердикт по счётчикам ядра давался по накопительному итогу.** Красный
  процент ретрансмитов и переполнение accept-очереди оставались на экране
  месяцами после того, как причина устранена, — та же ошибка подачи, что уже
  исправлена в блоке G. Теперь вердикт по окну с прошлого замера, накопительное
  печатается справочно и помечено как история.
- **Шаг DoT молча пропускался на серверах, где DoT включили до нас.** Первая
  правка сравнивала наш drop-in по содержимому — но если его нет вовсе, а DoT
  уже строгий, шаг печатал зелёную галочку и уходил. То есть резервирование
  апстримов, ради которого правка и делалась, до такого сервера не доезжало,
  и по выводу это выглядело как «всё применено». Теперь шаг читает
  ЭФФЕКТИВНУЮ конфигурацию (`systemd-analyze cat-config`, main + все drop-in),
  печатает список апстримов и предупреждает, если их меньше трёх. Переписывать
  чужое молча по-прежнему нельзя — для этого появилась отдельная команда
  `xm harden --dot`. Она находит файл, который фактически задаёт `DNS=`, и
  правит в нём одну строку — иначе рядом лёг бы второй drop-in, спорящий за ту
  же настройку, и кто победит, решало бы имя файла. После правки сверяет
  эффективный список: перекрытие файлом с именем позже видно сразу.
- **Второй inbound (TCP/Vision) не проверялся на достижимость снаружи.**
  Фронт его не обслуживает — маска общая, по одному SNI два потока не развести.
  Значит он либо открыт своим номером (и это ровно аномалия B8), либо закрыт —
  и тогда `xm qr --tcp` выдаёт URI, который у клиента не заработает, а
  `xm selftest --tcp` этого не покажет, потому что ходит через loopback.
  `diag-dpi` и `xm front status` теперь говорят об этом прямо.

### Ветка `claude/xm-update-dot-hardening-6gqxx4`

Подача блока G — счётчиков ядра:

- **Итог `diag-dpi` не учитывал блок G.** Обёртки со счётчиком объявлялись
  внутри самой команды, а счётчики ядра печатает функция, общая с `xm tune`, —
  для неё этих обёрток не существовало. В результате красный `[✗]` по
  ретрансмитам соседствовал с «Критично: 0»: итоговая строка противоречила
  собственному выводу, а она и есть то, по чему судят о прогоне. Обёртки
  подняты на верхний уровень, находки блока доезжают до итога.
- **`overflows` и `drops` печатались одним текстом.** `ListenDrops` растёт и
  без `ListenOverflows` — тогда до accept-очереди дело не дошло вовсе, и совет
  про её размер уводит не туда. Случаи разведены: переполнение accept-очереди
  и отказ раньше (полная SYN-очередь при выключенных syncookies, нехватка
  памяти на пике) — с разными подсказками.
- **Вердикт по UDP-буферу давался по счётчику с загрузки**, хотя снапшот
  хранит это поле с самого начала: предупреждение висело за давно прошедший
  пик — та же ошибка подачи, что уже исправлена для ретрансмитов и
  accept-очереди. Теперь по окну, накопительное справочно; тем же образом
  датированы TCP-таймауты. Отрицательная дельта (поле пропало из вывода
  `nstat`) держится на нуле, чтобы не выдавать артефакт за вердикт.

## 2. Ключевой вывод, из которого растёт остальное

REALITY дозванивается до `dest` **на каждое входящее соединение**, а `dest` в
nginx задан именем и резолвится в рантайме. Поэтому:

> сдох резолвинг → nginx не знает апстрим → REALITY некуда форвардить →
> сервер принимает TCP и молча рвёт

А «принял TCP и закрыл» — это подпись прокси, ради ухода от которой сделан
весь mimic-fallback. **Нестабильность здесь равна демаскировке**, это не две
разные темы. Xray при этом жив, systemd ничего не перезапустит — поэтому
проверять надо сквозной путь, а не статус юнитов.

## 3. Методические выводы из замеров

Конкретные числа остаются в чате; сюда вынесено только то, что меняет код:

- **Накопительный счётчик без датировки читается как текущее состояние.**
  Именно так прошлая сессия сделала сброс домена-маски ведущей гипотезой:
  блок G показывал итог за всё время жизни файла. Исправлено — вердикт по
  окну 24 ч плюс давность последнего реального отказа. То же для счётчиков
  ядра: добавлена точка отсчёта в `/var/lib`, вывод дельты, `xm tune` ставит
  точку заново.
- **Строки старого strict-режима (`no host in upstream`) надо отфильтровывать**,
  иначе они маскируют реальную картину отказов.
- **Холодный резолвинг `dest` занимает единицы секунд, тёплый — миллисекунды.**
  С `policy.handshake: 4` клиент, попавший в холодный кэш, не входит в окно.
- **Проверять командой, а не по памяти.** Предположение прошлой сессии, что
  TCP/443 свободен, оказалось неверным — порт занят другой службой. Само
  рассуждение «TCP и UDP на одном номере не конфликтуют» верно, но к
  фактическому состоянию отношения не имело.

## 4. Снято (проверялось, не подтвердилось)

- BBR отсутствует → включён.
- `LimitNOFILE` у юнита Xray мал → уже поднят официальным установщиком.
  У nginx это отдельная величина и она поднята не была — см. §1.
- `error_log` в stream течёт IP клиентов → нет, там `client: 127.0.0.1`.
- Xray нестабилен → рестартов нет.
- journald пишет клиентские IP → не пишет.
- Системный стаб без DoT → DoT включён, стаб закрыт. Именно строгий DoT и
  объясняет отказы резолвинга: при недоступном `:853` резолвед обязан вернуть
  ошибку, а не уйти в открытый UDP. Это правильное поведение; лечится не
  откатом, а `valid=900s` + watchdog.
- **Сбросы домена-маски как причина мигания на Android** → снято: событий
  порядка одного в сутки, а симптом — раз в пару секунд. Смена домена
  остаётся осмысленной по другим причинам (5.3), но к этому симптому
  отношения не имеет.

## 5. Открытые вопросы — с них продолжать

### 5.1. Выход на стандартный порт — ЗАКРЫТО
Фронт по SNI поднят, соседняя служба живёт за ним по своему домену, порт
inbound снаружи закрыт, B8 зелёный. Сертификат домена-маски больше не виден
на нестандартном номере — самый крупный оставшийся признак снят.

### 5.2. Мигание «соединение» в мессенджере на Android
Кандидаты 1 и 2 (не применён `xm tune`; переполнение accept-очереди) сняты
замером: профиль применён, MTU probing включён, в окне с прошлого замера
accept-очередь чистая. При этом доля ретрансмитов в окне остаётся высокой —
выше накопительной, то есть потери идут сейчас, а не остались из прошлого.
BBR и fq включены, значит алгоритм ни при чём: это либо последняя миля у
клиентов, либо участок пути от VPS.

Остаётся кандидат 3 — **`nonIPQuery: drop`**: Android с 11-й версии сам
запрашивает HTTPS/SVCB (тип 65), а `drop` отбрасывает такой запрос молча, и
клиент ждёт свой таймаут. Проверяется точечно, без отката всего harden:

```bash
sudo xm harden --nonip          # что принимает эта сборка Xray
sudo xm harden --nonip skip     # 10-15 мин пользования
sudo xm harden --nonip drop     # вернуть в любом случае
```

`skip` — режим на время проверки: запросы не-A/AAAA уходят с VPS открытым UDP.
Если мигание уходит именно на нём — виноват кандидат 3, и дальше надо искать
режим мягче `drop`, но без открытого UDP, а не оставлять `skip`.

**Эксперимент ещё не проведён.** Ручка работает, оба переключения проходят, но
между ними нужны 10–15 минут реального пользования телефоном: сам по себе
`skip → drop` подряд ничего не измеряет. Пока кандидат 3 ни подтверждён, ни
снят.

Разделитель по транспорту: переключить телефон на второй inbound
(`xm qr --tcp`). Осторожно с направлением вывода — TCP/Vision открывает
**больше** дозвонов до `dest`, чем XHTTP с мультиплексированием. Значит
«на TCP стало хуже» указывает на `dest`, а «на TCP стало лучше» — на XHTTP.

### 5.2a. `sniffing` без `routeOnly` — закрыто решением, кода не будет
На обоих inbound `sniffing.enabled: true` с `destOverride` и без `routeOnly`,
то есть найденный домен заменяет адрес назначения и сервер резолвит его сам.
Разбор показал, что менять это не надо:

- лишнего раунда почти нет: `dns.disableCache: false`, а адрес в подавляющем
  большинстве случаев уже в кэше — клиент получил его от нашего же DoH через
  перехват :53;
- `destOverride` здесь ещё и защита: клиент, у которого DNS идёт мимо тоннеля,
  приносит адрес от резолвера провайдера, то есть потенциально подменённый.
  Пересоздание адреса по имени на сервере это отменяет, `routeOnly: true` —
  наоборот, заставило бы идти по клиентскому адресу.

Возвращаться сюда стоит, только если замер покажет, что резолвинг реально
происходит на каждое соединение (то есть кэш не работает).

### 5.3. Смена домена-маски
По замеру `xm sni-scan` текущий домен выигрывает у всех кандидатов и по
размеру сертификата, и по RTT, а его редкие сбросы (порядка одного в сутки)
к миганию отношения не имеют — это снято в §4. Менять по техническим
причинам нечего.

Осталась одна нетехническая: он же самый растиражированный REALITY-dest в
мире, и «адрес, отдающий его сертификат, но не принадлежащий его сети» —
дешёвая эвристика для перечисления. Альтернативы из пула проходят все пороги,
платя за это большим сертификатом и худшим RTT. Решение владельца; критерии
прежние: TLS 1.3 + ALPN h2 обязательны, сертификат с запасом до лимита буфера
REALITY, низкий RTT.

### 5.4. Маскировка `Server` на `:80` — ЗАКРЫТО
Модуль headers-more поставлен, `harden` привёл `:80` к виду домена-маски,
B7 зелёный: `Server` совпадает, редирект ведёт на имя.

### 5.5. Резервирование апстримов DoT
Профиль DoT на сервере есть, но лежит в drop-in с ДРУГИМ именем, не по нашему
пути: содержимое при этом наше, просто перенесённое руками. Отсюда и промах
предыдущей правки — она искала файл по пути.

Апстримов там два. Под строгим DoT недоступность одного провайдера означает не
замедление, а отказ резолвинга, то есть мёртвый `dest` и подпись прокси до
срабатывания watchdog. `xm harden --dot` теперь находит файл, который
фактически задаёт `DNS=`, и правит в нём одну строку — второй drop-in,
конкурирующий за ту же настройку, не заводится.

Общий вывод на будущее: **свои артефакты опознавать по содержимому и по
эффективной конфигурации, а не по пути.** Путь — предположение, которое
владелец мог изменить, а проверка по пути даёт ложное «настроено не нами».

## 7. Правила работы по этому проекту

- Отвечать по-русски. Активировать скилл `xray-dpi` (`.claude/skills/xray-dpi/`).
- Сначала команды проверки → дождаться результатов → только потом код.
  После правок — команды, которыми владелец убедится в эффекте.
- Минимум изменений в существующие файлы, без дублирования.
- Команды, требующие прав, писать с `sudo`.
- `setup.sh` идёт под `set -euo pipefail`: `grep` без совпадения возвращает 1
  и роняет конвейер. `xm.sh` под `set -e` **не** идёт — поведение разное.
- Никаких идентификаторов установки в коде, README, коммитах и PR — полный
  список и порядок проверки в скилле `xray-dpi`.
