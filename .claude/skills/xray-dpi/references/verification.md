# Проверка правки: уровень, VPS, отчёт

## Содержание
0. Уровень проверки
1. Снимок состояния до правок
2. Тест должен доказывать изменение, а не сопровождать его (+ скрипт на VPS, минимум перед push)
3. Долгие замеры — фоном на VPS
4. Порядок перед PR
5. Панель (`xm ui`) и статистика (`xm stats`)

## 0. Уровень проверки

Наименьший уровень, который доказывает эффект правки; выше — только если нижний не может.
Отчёт `code_pr / checks / integration / merge_ready` — `AGENTS.md`, «Ответ: коротко и с вердиктом».
Что писать в тест и где уместен мок — `.claude/rules/tests.md`.

| Правка | Чем доказывается | `integration` |
|---|---|---|
| Инструкции, README, комментарии, тексты `xm help` | `bash tests/check.sh` | NOT_REQUIRED |
| Логика без внешнего состояния: разбор вывода, аргументы, вычисления | + функция на входах-образцах в песочнице, с пустым и неразобранным входом | NOT_REQUIRED |
| Сборка конфига Xray / nginx, jq-патчи | + `xray -test` / `nginx -t` на собранном конфиге той версии, что на сервере | NOT_REQUIRED, если версия известна и от состояния сервера не зависит |
| Состояние системы (ufw, nginx, systemd, sysctl, DNS, сокеты), доступность снаружи, клиент, ТСПУ | скрипт на живом VPS, §2 | PASS / FAIL / NOT_RUN |

Сомнение между строками — нижняя: ложный PASS дороже прогона. Доступа к VPS у агента нет —
скрипт запускает владелец. Зелёный `bash -n` и логичный дифф правку состояния не доказывают:
здесь уже был случай, когда `front on` поднимал сокет, `front status` показывал «порт держит
nginx», `diag-dpi` был полностью зелёным, а снаружи не подключался никто: правило UFW не
ставилось, а зонды шли через `lo` и файрвол не трогали.

## 1. Снимок состояния до правок

Собери максимум контекста **одним пакетом**, а не по команде за раунд:
пользователь выполняет их на VPS и присылает вывод.

База (бери релевантное задаче, не весь список подряд):

```bash
sudo xm info            # что вообще настроено
sudo xm journal         # что на этом сервере уже разбиралось и чем кончилось
sudo xm diag-dpi        # устойчивость к DPI, блоки A–G
sudo xm selftest        # сквозной путь
sudo xm diag-ports      # кто какой порт держит на самом деле
sudo xm harden --check
sudo xm tune --check
sudo xm front status
sudo xm neighbors       # что ещё живёт на сервере
sudo xm stats status    # статистика для панели: API, таймер, последний замер
```

`xm journal` в этот пакет входит всегда, не только «по релевантности задаче»:
он может показать, что найденная проблема уже разбиралась и снималась раньше
на этом же сервере, — это меняет, стоит ли вообще идти дальше по гипотезе.

Версии — потому что фича из свежего релиза на установленной версии не
заведётся:

```bash
xray version; nginx -v; sudo xm self-update --check; uname -r; lsb_release -ds
```

С клиента — приложение, версия его ядра Xray, оператор и тип сети, `fp` из URI:
пускает ли клиента REALITY сервера, решает именно ядро клиента (`landscape.md`).

Плюс точечно то, что должна изменить именно эта правка: конкретный счётчик,
конкретные строки лога, конкретный сокет. Без снимка «до» доказать эффект
будет нечем.

Вывод с живого сервера — контекст чата. В коммиты, README и PR он не
попадает (см. «Публичный репозиторий» в `AGENTS.md`).

## 2. Тест должен доказывать изменение, а не сопровождать его

Тест считается доказывающим, если выполнено хотя бы первое и одно из
остальных:

- **есть замер «до» и «после»** на том же сервере, и они различаются в
  ожидаемую сторону;
- **есть негативная проверка**: выключи правку (`--off`, `restore`, откат
  файла) — показатель возвращается к прежнему значению;
- **путь совпадает с клиентским**: зонды с самого VPS на его же внешний
  адрес идут через `lo` и проходят мимо ufw. Всё, что касается доступности
  снаружи, проверяется с клиента, а не с сервера;
- **проверяется следствие, а не статус юнита**: `systemctl is-active` жив и
  при мёртвом резолвинге `dest`.

### Скрипт на VPS

Уровень §0 требует VPS — в PR идёт `tests/vps/<тема>.sh` на `tests/lib.sh` (функции — в шапке
`lib.sh`). Скрипт сам сравнивает ожидаемое с фактическим и печатает отчёт; код выхода 0 — только
при `merge_ready: YES`. PASS без `vpr` (на сервере код этой ветки), без проверок, при таймауте и
при обрыве до `vreport` не выдаётся — это держит харнесс, а не аккуратность автора.

Проверять инварианты правки, а не «команда отработала»:

- эффект — значение после действия (`vexpect`);
- целостность — то, что правка трогать не должна: клиенты, inbounds, правила ufw, слушающие
  сокеты (`vsnap` до действия, `vsame` после: полное сравнение, в отчёт — счёт и первые
  расхождения);
- конфиг принят, сквозной путь жив; негатив и откат: выключить правку — показатель вернулся;
  повторный запуск — без дублей;
- доступность снаружи зондом с VPS не доказать (идёт через `lo`): правило файрвола и
  соединение клиента, видное на сервере (`ss` с не-петлевого адреса, `VTIMEOUT=180`, пока
  владелец подключается);
- в `vcheck` — только команды с честным кодом выхода: `xm test` при невалидном конфиге выходит
  с 0, вместо него `xray -test -config`; не уверен — `vexpect` по выводу.

Включённое только ради проверки скрипт выключает: сервер остаётся рабочим.

```bash
#!/usr/bin/env bash
# <что доказывает>. Запуск: sudo bash tests/vps/<тема>.sh
source "${BASH_SOURCE[0]%/*}/../lib.sh"
CFG=/usr/local/etc/xray/config.json
vpr
vsnap "$VTMP/clients" jq -c '.inbounds[].settings.clients[]?' "$CFG"
vcheck  "<действие>"     xm <команда правки>
vexpect "<эффект>"       "<ожидаемое>"  bash -c '<команда, печатающая факт>'
vcheck  "конфиг принят"  xray -test -config "$CFG"
vcheck  "сквозной путь"  xm selftest
vsame   clients "$VTMP/clients"  jq -c '.inbounds[].settings.clients[]?' "$CFG"
vreport
```

Владельцу — одна команда: подготовка и запуск через `&&`, все проверки — в скрипте. Повторный
прогон после новых коммитов ветки — та же строка: `xm self-update` переводит чекаут на
`origin/<ветка>`. После слияния — вернуть сервер на main (иначе обновления до него не дойдут):

```bash
cd /opt/xray && sudo git fetch -q origin && sudo git checkout -q <ветка> && sudo xm self-update && sudo bash tests/vps/<тема>.sh
# после слияния PR
cd /opt/xray && sudo git checkout -q main && sudo xm self-update
```

Присланный вывод — отчёт как есть: поля не пересчитываются и не дополняются.

### Минимум перед push

- [ ] `bash tests/check.sh` — PASS (синтаксис, скиллы, тесты, данные установки в ветке)
- [ ] целевая проверка правки по уровню §0 — поле `code_pr`; для кода — с откаченной правкой
      она падает
- [ ] `xray -test` / `nginx -t` там, где менялся конфиг
- [ ] повторный запуск не ломает и не дублирует (идемпотентность)
- [ ] путь отката проверен, а не только написан
- [ ] уровень требует VPS — скрипт `tests/vps/<тема>.sh` в PR; правка касается подключения — клиент
      подключается с клиентской ОС и из той сети, где была проблема: ТСПУ у операторов
      (мобильный, проводной) ведёт себя по-разному
- [ ] инструкции синхронизированы с правкой (`AGENTS.md`, «Инструкции меняются
      вместе с кодом»)

Не прогнано на VPS, когда уровень этого требует, — `integration: NOT_RUN`, `merge_ready:
UNKNOWN` и строка в HANDOFF §3.1: что не проверено и каким скриптом.

## 3. Долгие замеры — фоном на VPS

Интерактивный тест, где пользователь сидит у экрана и что-то делает на
клиенте, должен укладываться **в пару минут**. Всё, что дольше, оформляется
как фоновый сбор на сервере.

Фоновый замер обязан:

- пережить закрытие SSH и выключение компьютера пользователя;
- писать результат с метками времени;
- сам остановиться по таймеру, а не висеть вечно;
- читаться потом одной короткой командой.

Шаблон — `systemd-run` (он уже используется в `xm.sh`, даёт таймер, единое
место для вывода и остановку одной командой):

```bash
sudo systemd-run --unit=xm-probe --collect \
  --property=RuntimeMaxSec=3600 \
  /bin/bash -c 'while :; do echo "$(date -Is) $(<команда замера>)"; sleep 60; done'
```

Забрать результат позже — в любой момент, с любого устройства:

```bash
sudo journalctl -u xm-probe --no-pager | tail -50
sudo systemctl status xm-probe          # ещё идёт или уже отработал
sudo systemctl stop xm-probe            # остановить досрочно
```

Если вывод объёмный и нужен файлом, а не в журнале:

```bash
sudo systemd-run --unit=xm-probe --collect --property=RuntimeMaxSec=21600 \
  /bin/bash -c 'exec >>/var/log/xm-probe.log 2>&1; while :; do date -Is; <команда>; sleep 300; done'
```

`nohup … &` тоже переживает выход из SSH, но не даёт ни таймера, ни
остановки по имени. `screen`/`tmux` не годятся: требуют, чтобы пользователь
помнил про сессию и вернулся именно в неё.

Запуская фоновый замер, скажи одной строкой: что запущено, сколько идёт,
чем посмотреть результат, чем остановить. Файл `/var/log/xm-probe.log`
после разбора удалять — в нём адреса и порты живой установки.

## 4. Порядок перед PR

1. Минимум §2 закрыт; нужен VPS — скрипт `tests/vps/<тема>.sh` в PR, строка в HANDOFF §3.1.
2. Только теперь `commit` и `push`: `tests/check.sh` (данные установки в ветке — в нём)
   прогоняет перед ними хук `commit-guard.sh`.
3. PR оформляется по `references/publishing.md` — отчёт и тесты остаются в ответе, в
   тело PR они не переносятся.

## 5. Панель (`xm ui`) и статистика (`xm stats`)

Эффект доказывается на VPS и с ПК, а не чтением кода панели:

- слушает только петлю: `sudo ss -tlnp | grep python3` — адрес 127.0.0.1; то же говорит
  `sudo xm diag-dpi`, блок I. Негативная проверка обязательна: фальшивый слушатель на
  `0.0.0.0` с `server.py` в командной строке должен дать `[✗]`;
- снаружи недоступна: с ПК `curl -m 5 http://<адрес VPS>:<порт панели>/` — таймаут, не ответ;
- через тоннель: без токена пустой 404, с токеном — страница; после Ctrl+C порт закрыт;
- `sudo xm stats on`: `xm stats status` зелёный; через 5–10 минут реального пользования в
  панели виден трафик клиента. `sudo xm stats off` возвращает конфиг (`jq '{stats,api}'
  /usr/local/etc/xray/config.json` — оба `null`) и стирает `/var/lib/xm/stats`;
- Xray при `stats on` перезапускается: убедиться, что клиент на телефоне переподключился сам.
