# Актуальная картина: ТСПУ, Xray, клиенты

**Проверено: 2026-10-06.** Здесь всё, что устаревает: поведение цензора, версии, умолчания и

## Как обновлять

1. Вес источников: код и коммиты XTLS (Xray-core, REALITY, Xray-docs-next) и `xray -test` на
   версии сервера → замеры с данными (net4people/bbs, ntc.party, te-st.org, issues XTLS с
   логами) → обзоры (Хабр и т.п.) как повод проверить, а не как факт. Каталоги «лучший VPN
   2026» источником не считаются.
2. Каждой строке — месяц и ссылка. Сообщение одного пользователя без подтверждения помечать
   «отчёт».
3. Источник недоступен из песочницы (часть сайтов режет egress) — пересказ из поиска помечать
   «по пересказу». Публичный исходник XTLS клонируется и читается напрямую.
4. Снятое не удалять: переносить в «Устарело» с датой и причиной.
5. Код опирается на строку отсюда (порог, версия, умолчание) — в той же правке сверить
   комментарий в коде и эту строку.

Где смотреть: github.com/XTLS/Xray-core (releases, commits, issues), github.com/XTLS/REALITY
(commits), github.com/XTLS/Xray-docs-next, github.com/net4people/bbs/issues, ntc.party,
te-st.org.

## Цензор (РФ): что видит и что делает

- **2022–2026** — QUIC/HTTP3 к зарубежным адресам режется у части операторов (например, Tele2
  мобильный): UDP-протоколы годятся как резерв, не как основа. — ntc.party; FOCI 2026 «On
  Russia's Early Introduction of QUIC SNI Censorship».
- **2024-11** — ECH (Cloudflare) блокируется. — Cloudflare/AdGuard, 2024-11.
- **2025-06 →** — заморозка TCP после ~16–20 КБ / ~25 пакетов к адресам хостинговых ASN: без
  RST, протокол не важен; позже — разрешение по CIDR назначения. — net4people/bbs#490.
- **2025 →** — белые списки мобильного интернета (IP + SNI), во многих регионах постоянно;
  рабочего обхода публично нет, адреса российских облаков тоже не спасают (2026-08). —
  net4people/bbs#650, #579.
- **2025-11** — первые блокировки VLESS+REALITY по сигнатуре; на сервере «failed to read
  client hello». — XTLS/Xray-core#5332; xakep.ru 2025-12-05.
- **2026-02-17** — косвенные признаки: SNI не совпадает с сетью сервера, нетипичный паттерн
  соединений; проводные Дом.ру, SkyNet, Ростелеком. — The Moscow Times 2026-02-17; te-st.org №37.
- **2026-04-15** — крупные российские сервисы обязаны выявлять VPN у пользователей и
  ограничивать доступ (методика Минцифры; на iOS и при раздельной маршрутизации выявление,
  по самой методике, ограничено). — The Moscow Times 2026-04-06; istories 2026-04-07.
  Сервисы ещё и помогают находить VPN, которых РКН не знает: IP пользователя сверяют с
  российскими диапазонами и списком заблокированных — то есть адрес сервера, пришедший
  к сервису через тоннель, становится находкой. — РБК через Хабр и securitylab 2026-04
  (по пересказу).
- **2026-04** — у VLESS-клиентов локальный SOCKS5 без пароля: любое приложение на устройстве
  ходит через него и узнаёт IP сервера. — xakep.ru 2026-04-07.
- **2026-05…06** — волны по регионам; «заморозка по отпечатку» (отчёт): больше 3 параллельных
  TLS-хендшейков к серверу за 60 с → 120 с заморозки, смена отпечатка во время неё → 600 с на
  любой TLS; отпечатки chrome/safari/ios помечались, firefox/android/okhttp/edge у большинства
  операторов проходили; под раздачу попадали и российские облака (Selectel, Yandex Cloud,
  Cloud.ru). — XTLS/Xray-core#6293 (2026-06-08); Хабр «Заморозка по fingerprint» (по пересказу).
- **2026-08-04, 2026-09-21** — массовые баны IP хостеров (тысячи адресов), включая REALITY с
  self-steal и серверы только с AmneziaWG, то есть не по активному зондированию; в отчёте —
  популярные у VPN хостеры (Amnezia Hosting, FirstByte, Fornex, Play2Go DE, VEESP: от сотен
  до тысяч адресов каждого). — net4people/bbs#671; te-st.org №37.
- **2026-08-26** — UDP/53 к зарубежным резолверам (8.8.8.8) подменяется у ряда провайдеров
  сразу: для заблокированных имён — NXDOMAIN или адреса MSK-IX, TCP/53 при этом честный. —
  net4people/bbs#657 (отчёт).
- **2026-09-02** — после включения TUN-режима v2rayN на Windows (мобильный Билайн) через
  5–15 мин связь деградирует до белого списка на всех устройствах точки; на Android того же
  нет. Причина не установлена. — net4people/bbs#663 (отчёт).

## Xray и REALITY: версии, умолчания, пороги

Проверено по исходникам тегов, если не сказано иное.

- **Стабильный (Latest) — v26.3.27**: всё после него, v26.5.3…v26.9.30, выходит как
  pre-release. `install-release.sh` (setup.sh, `xm update`) без `--beta` ставит Latest — то есть
  по умолчанию сервер на v26.3.27, и пороги, умолчания и проверки ниже, помеченные версией
  новее, на нём не действуют. — github.com/XTLS/Xray-core/releases (2026-10-06).

- **v25.7.26** — пресет chrome шлёт X25519MLKEM768. — стенд владельца, коммит e6955c8.
- **v25.9.5** — VLESS Encryption (ML-KEM-768) в стабильном релизе. — XTLS PR #5067.
- **v26.3.27** — firefox/safari с X25519MLKEM768 (раньше это Firefox 120 и Safari 16);
  Hysteria2 inbound и транспорт; finalmask (fragment, noise, header-custom, sudoku, salamander,
  xdns…); Xray сам предупреждает про порт ≠ 443 и маски apple/icloud (в пре-релизах — с
  v26.3.23, по нему сверяется `xm diag-dpi` A3). — релиз v26.3.27.
- **v26.6.27** — XHTTP: xmux по умолчанию `maxConnections` 6. — коммит 18b85ad.
- **v26.7.11** — REALITY: `minClientVer` по умолчанию 26.3.27 — ядра клиента старше и чужие
  ядра (mihomo) получают отказ. — коммит af7eb68; XTLS/Xray-core#6477.
- **v26.7.28** — `maxConnections` по умолчанию 3 («anti-TSPU»); в предупреждения добавлены
  microsoft и зоны .ru/.ir/.cn. — коммит 18e2839; infra/conf.
- **v26.9.8** — REALITY 8cdf7bf: ClientHello без X25519MLKEM768 перед X25519 уходит в fallback
  (у клиента таймаут, в логе «processed invalid connection»); `minClientVer` по умолчанию снят;
  буфер записи target 8192 → 17 408 б (393f8de, предок 8cdf7bf).
- **v26.9.30** — последний pre-release на дату проверки; REALITY та же (8cdf7bf);
  `nonIPQuery`/`blockTypes` dns-outbound ещё принимаются, но устарели → `rules`, смешивать нельзя.
  В `main` после него (по 2026-10-05) — WireGuard, XDNS finalmask, Mux, gRPC; REALITY и XHTTP
  не тронуты. — git log v26.9.30..main.
- **v26.1.13 → v26.2.6, 2026-07** — `pinnedPeerCertSha256` вместе с `allowInsecure`
  пропускал MITM (GHSA-5wf9-h793-w73c): тихая правка в v26.2.6, неполная, закрыта после
  2026-07-03. Касается TLS с самоподписанным сертификатом, не REALITY. —
  net4people/bbs#672 (2026-10-02).

Постоянное (на v26.9.30):

- `target` — нынешнее имя `dest` (старое принимается); у клиента `password` — бывший `publicKey`.
- Xray предупреждает при `xray -test`: порт ≠ 443; serverNames на .ru/.ir/.cn или со словами
  apple/icloud/microsoft («increase the likelihood of your server's IP being blocked»).
- `mldsa65Seed` требует у target запись Certificate не меньше ~3.5 КБ.
- Прошедший проверку клиент соединения к target не держит: REALITY закрывает его до того, как
  вернуть соединение Xray; висит оно только у не прошедших (зонды). На этом `xm diag-dpi` G5
  отличает сканер от шторма своего клиента. — XTLS/REALITY tls.go (3c98159, 2026-09-21).
- `limitFallbackUpload/Download` — лимит скорости соединений, не прошедших аутентификацию:
  их REALITY отдаёт target, и без лимита сервер — бесплатный канал к сайту-маске. Но сам
  лимит — отпечаток, и документация XTLS его не рекомендует: только при маске на бесплатном
  CDN, а лучшая практика — сосед по ASN. В установке не задаётся сознательно. —
  Xray-docs-next, transports/reality.md (f2b3064, 2026-10-03).
- XHTTP: автор советует задавать только `path`. Пустой `xmux` → дефолты (`maxConnections` 3,
  `hMaxRequestTimes` 600–900, `hMaxReusableSecs` 1800–3000); задан хоть один параметр — у
  остальных дефолтов нет. С REALITY `auto` = `stream-one`, с `downloadSettings` — `stream-up`.
- Открытая ошибка: клиентские ядра v26.9.8+ (сборки Go 1.27) — `maxConnections` не держит
  лимит, когда хендшейки зависают: по соединению на сессию, вплоть до OOM. Обход — сборка с
  `-tags http2legacy`; ядра по v26.7.28 включительно собраны Go 1.26 и ошибки не несут. —
  XTLS/Xray-core#6797 (открыта на 2026-10-06, последняя активность 2026-09-21; go.mod тегов).

## Клиенты

- С сервером ≥ v26.9.8 работают: ядро Xray ≥ v25.7.26 с fp `chrome`; `firefox`/`safari` — ядро
  ≥ v26.3.27. v2rayN (Windows, macOS), v2rayNG (Android), Happ (iOS, macOS) — при свежем ядре.
- Не проходят до своих патчей: sing-box (Hiddify, NekoBox, Karing) — sing-box#4520,
  Karing#1952; mihomo — отказ уже с v26.7.11. Проверять конкретную версию клиента.
- Hiddify 4.1.1 (2026-03-05, последний на 2026-10-06): ядро — свой форк sing-box, XHTTP с
  4.0.5. Со стабильным сервером v26.3.27 по XHTTP работает (замер владельца, 2026-10). Пускает
  ли его REALITY ≥ v26.9.8, не проверено: до проверки сервер на pre-release не переводить. —
  github.com/hiddify/hiddify-app/releases; apkmirror, «What's new in Hiddify 4.0.5».
- Пресеты edge, ios, android, randomized и подобные — без X25519MLKEM768 или не браузерные:
  REALITY ≥ v26.9.8 их не пускает.
- Ядро клиента v26.9.8+ несёт открытую #6797: при зависающих хендшейках клиент плодит
  соединения — а это и есть признак для ТСПУ. Всплеск соединений с одного клиента (`xm
  diag-dpi`, G5) — сверить статус #6797 и версию ядра клиента. Пока ошибка открыта, ядро
  v26.7.28 с fp `chrome` — рабочий откат: Go 1.26, maxConnections 3, сервер ≥ v26.9.8 его
  пускает; в v2rayN ядро меняется файлом, в мобильных клиентах оно встроено. — go.mod тегов.
- Открытый локальный SOCKS5 (2026-04): v2RayTun, V2BOX, v2rayNG, Hiddify, Exclave, NekoBox,
  типовые Clash/sing-box. Защита: TUN без SOCKS наружу, пароль на локальный прокси, где клиент
  умеет, запрет доступа из LAN, обновление клиента.

## Что из этого следует для установки

- Маска: self-steal (свой домен, A-запись на этот сервер, настоящий сертификат и сайт)
  снимает расхождение SNI и сети полностью; сосед по ASN (`xm sni-scan --local`) — только на
  уровне ASN; чужой CDN — расхождение всегда. Цена self-steal: домен связывает владельца с
  сервером (регистрация, оплата) — для анонимности довод против, решает владелец.
- Транспорт: XHTTP+REALITY на 443 при дефолтном xmux (ядро клиента ≥ v26.7.28) держит до
  трёх долгих соединений с мультиплексом; TCP/Vision открывает хендшейк на каждое
  соединение — ровно признак «много параллельных TLS». Vision — только по необходимости,
  xmux у клиента без замера не трогать.
- Отпечаток: `chrome` проходит REALITY ≥ v26.9.8. Если у оператора клиента chrome
  «замораживается» — `firefox` на ядре ≥ v26.3.27: единственный пресет, совместимый с обоими
  ограничениями. Во время заморозки отпечаток не менять.
- Порт — только 443.
- Бан IP/ASN, заморозка подсети конфигом не лечатся. Готовность: запасной сервер у другого
  провайдера и ASN, несколько URI в клиенте с автопереключением, быстрая переустановка.
- Клиент: российские адреса и домены — напрямую, мимо тоннеля (иначе сервисы, обязанные искать
  VPN, видят IP сервера); TUN вместо системного прокси (UDP/WebRTC, IPv6); локальный прокси —
  без доступа извне. Решение «напрямую» — по адресу, полученному через тоннель или DoH:
  DNS провайдера подменяет ответы для заблокированных имён (#657), и заблокированный сайт
  ушёл бы мимо тоннеля.
- Сервер: geoip:ru из тоннеля — в blackhole (`xm harden`, правило `xm-ru`) — страховка на
  случай, когда клиент этого не сделал. По адресу, не по `geosite:category-ru`: в нём вся
  зона .ru, включая заблокированные в РФ сайты, ради которых нужен VPN. — v2fly
  domain-list-community, data/category-ru (include:tld-ru), 2026-10-04.
- VLESS Encryption — когда TLS снимает посредник (CDN, мост в РФ); REALITY не заменяет.
- Канал другого класса (Hysteria2 в Xray) — только запасной: UDP режется у части операторов.

## Чего не обещать

- Обход белых списков мобильного интернета настройкой сервера.
- Лечение бана IP/ASN или заморозки подсети правкой конфига.
- CDN как спасение: крупные зарубежные CDN сами под заморозкой, ECH заблокирован.

## Устарело

- 2026-09 — «буфер записи target у REALITY — 8192 б»: верно для Xray < v26.9.8, с v26.9.8 —
  17 408 б. С 2026-10 в коде порог по версии на сервере (`_cert_limits`): 8192/7000 до
  v26.9.8, 17 408/16 384 с неё.
- 2026-09 — «chrome на ядре от v25.7.26 пускает любой сервер»: v26.7.11–v26.7.28 требовали
  ядро клиента ≥ v26.3.27 (`minClientVer` по умолчанию); с v26.9.8 этот дефолт снят.
