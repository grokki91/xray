## 0. Резюме

Что строим: приложение `xdiag` для Windows 11 — одна кнопка «Диагностировать», под ней
диагностическое ядро на Go. Ядро собирает улики с четырёх источников, сопоставляет их по
декларативным правилам и выдаёт одну причину с уровнем уверенности, уликами и следующим шагом.

Ключевые решения (каждое обосновано в разделах ниже):

1. **Гибрид «автономно + SSH-мост + ручной обмен».** Автономная диагностика работает всегда;
   SSH-мост к `xm` — когда настроен ключ (у владельца он есть: панель `xm ui` уже живёт через
   `ssh -L`); ручной обмен файлом `doctor.json` — резерв, когда SSH недоступен (§2–3).
2. **Эталонное ядро внутри приложения.** Xray-core подключается как Go-библиотека и выполняет
   одну настоящую попытку VLESS+REALITY+XHTTP с профилем пользователя. Эталон прошёл, Hiddify —
   нет: причина в клиенте. Эталон не прошёл: причина в сети, сервере или профиле. Без эталона
   «таймаут» клиента неразличим (§3.2).
3. **Сервер — только чтение, новый код сервера минимален.** Одна новая команда `xm bridge`
   (allowlist: `facts`, `doctor`, `health`), sudo-правило без пароля только на неё, вывод без
   секретов и адресов; `xm doctor --json` и `xm health --json` переиспользуются как есть (§4, B).
4. **Таймаут ≠ блокировка.** Гипотеза «ТСПУ» подтверждается только сравнением: эталонные хосты
   из той же сети, тот же SNI на настоящем адресе маски, стадия обрыва с сервера (`xm doctor`)
   или воспроизведение из другой сети. Иначе — «вероятно», с названной проверкой (§7).
5. **Бюджет активных проб.** Приложение само не должно выглядеть как шторм: не больше трёх
   TLS-хендшейков к серверу за 60 с, включая попытки клиента в окне корреляции (§C, §10).
6. **Секреты не покидают машину.** UUID, pbk, shortId, путь, URL подписки — только хэши с солью
   сессии; история — в `%LOCALAPPDATA%` под DPAPI; экспорт — по умолчанию без адреса сервера (§8).
7. **Два репозитория, один контракт.** Приложение — в `xray_client`; `xm bridge`, поле
   `schema` в JSON и VPS-тест — в `xray`. Контракт версионируется, фикстуры вывода сервера
   живут в клиентском репозитории и ломают сборку при расхождении (§5).
8. **Стек: Go + Wails (WebView2).** Go — потому что Xray-core, uTLS и sing-box — на Go, и
   эталонная проба и разбор ClientHello получаются из тех же библиотек, что у клиентов (§9).

Первый кейс, который MVP обязан распознать: Hiddify 4.1.x (ядро — форк sing-box 1.13) не
проходит REALITY сервера на Xray ≥ v26.9.9 — ClientHello без X25519MLKEM768 уходит
сайту-маске, клиент пишет «таймаут». На сервере владельца это ровно текущая ситуация
(обновление до v26.10.21 от 2026-10-27, `landscape.md`). Приложение это не чинит, но называет
за 10 секунд и без сервера.

### 1.2. Почему «Таймаут» ничего не говорит

REALITY по построению молчит: не прошедший проверку ClientHello уходит сайту-маске, клиент
получает настоящий сертификат маски и закрывает соединение. В логах сервера пусто (это штатная
ветка протокола, не ошибка — комментарий в `xm.sh`, раздел «Локальный тоннель»). Ядро Xray на
клиенте в этом случае пишет `REALITY: received real certificate (potential MITM or redirection)`
и возвращает `REALITY: processed invalid connection` (transport/internet/reality/reality.go,
main на 2026-10-28); ядро sing-box — `reality verification failed`. Приложения-обёртки
показывают пользователю «Таймаут» или «Подключение…».

Одно и то же слово «таймаут» у клиента рождается минимум в восьми ситуациях:

| # | Где на самом деле | Что видит сервер |
|---|---|---|
| 1 | Клиент не поднял ядро/службу (TUN, порт занят, антивирус) — попытки нет вовсе | ничего |
| 2 | Профиль указывает не туда (адрес, порт, импорт испорчен) | ничего или чужой порт |
| 3 | SYN режется по пути (бан IP, белый список мобильной сети, файрвол роутера) | ничего |
| 4 | SYN дошёл, SYN-ACK не вернулся | `server.syn` / `net.synack` |
| 5 | TCP есть, ClientHello не дошёл или дошёл частично (DPI по SNI, MTU) | `net.hello` |
| 6 | ClientHello дошёл, REALITY отверг: нет X25519MLKEM768, чужой ключ, старый shortId, не тот SNI, часы | `client.core`, `profile.*`, `client.clock` |
| 7 | REALITY принял, ответ сервера до клиента не доходит (заморозка после хендшейка или на 10–32 КБ) | `net.freeze` / `net.f16` |
| 8 | Тоннель работает, не работает то, что за ним: DNS внутри, маршрутизация, тест задержки по URL | `ok` |

Серверный `xm doctor` различает 4–8, но не видит 1–3 (на сервер ничего не приходит) и не
отличает 1 от 3. Клиентская диагностика видит 1–2 полностью, 3 — сравнением, 6 — эталонной
пробой, 7–8 — частично. Ни одна сторона в одиночку не закрывает таблицу; отсюда — гибрид.

### 1.3. Что уже есть на сервере и переиспользуется

**`xm doctor [--live СЕК|--no-live] [--json]`** (`xm.sh` раздел «Почему клиент не
подключается», `ui/doctor.py`):

- факты сервера: самопроверка через публичный порт (`_health_selfcheck`: listen → резолв
  маски → настоящий VLESS-клиент на петле → запрос наружу), состояние UFW для порта, версия Xray;
- окно захвата (AF_PACKET + BPF по порту, по умолчанию 60 с): по каждой попытке стадия
  `syn | synack | scan | tcp | partial | nottls | hello`, для `hello` — повтор решения REALITY
  ключом сервера в порядке tls.go (`ok | tls13 | sni | mlkem | key | ver | time | sid`),
  признак `own` (session_id открылся ключом сервера — профиль с этого сервера), версия ядра
  клиента из session_id (`core_name`: Xray x.y.z / sing-box 1.8.1 / mihomo 1.8.2), и что было
  после (`post | mid | f16 | late | closed | flow`);
- группировка попыток по сетям /24 и /48 буквами, флаг `ssh` — сеть SSH-сеанса владельца
  (`XM_SSH_PEER`), адреса на диск не пишутся;
- хронология по журналу здоровья и история профиля по бэкапам `config.json` (`profile_sig`:
  хэши sha256[:12] порта, клиентов, ключа, shortIds, SNI, пути);
- вердикт — один код из 21 (приложение A), с `evidence[]`, `actions[]`, `ruled_out[]`;
- `--json` — весь отчёт одним объектом; поля `schema` пока нет.

**`xm health`** (`ui/health.py`): раз в минуту — tcp_info соединений на публичном порту
(классы `norm | pre | post | mid | f16 | late`), раз в 5 минут — окно: самопроверка, дельта
счётчиков ядра, логи nginx, события (перезапуск, смена конфига, версия), трафик своих клиентов;
вердикт окна `ok | server | freeze | degraded | suspect | nodata | monitor`; `xm health --json` —
полоса 24 ч, 7 дней, инциденты, события. Прямо пригодно как «что происходило на сервере в
момент попытки» и как источник «последний трафик клиента».

**Остальное:** `xm selftest` (живой хендшейк через петлю), `xm diag-dpi` (блоки A–I: маска,
зонды, REALITY, DNS, путь, штормы), `xm info --json` (версия, порты, SNI, fp, режимы harden),
`xm clients --json` (UUID и URI — через мост не выдаётся), панель `xm ui` (только 127.0.0.1,
токен в URL, через SSH-туннель; API `api/health`, `api/run selftest|diag-dpi`).

Чего сервер не видит и видеть не может: всё, что происходит до прихода SYN на его интерфейс;
какие попытки принадлежат именно этому ПК, если session_id не открылся (чужой ключ — это
`own=false`); локальное состояние клиента.

### 1.4. Границы

В задаче: Windows 11, Hiddify и v2rayN, сервер этого репозитория; диагностика и рекомендация.
Вне задачи: автоматическое исправление (правка профилей, маршрутов, DNS, файрвола клиента);

## 2. Сравнение архитектурных вариантов

| Критерий | 1. Автономный клиент | 2. Ручной обмен пакетами | 3. Автоматический защищённый мост |
|---|---|---|---|
| Покрывает строки таблицы §1.2 | 1, 2 полностью; 3 — сравнением; 6 — эталоном, но без различения key/sid/sni; 7 — по эталону частично | + 4–7 точно, если владелец запустил `xm doctor` в нужное окно | + 4–7 точно, окно синхронизировано автоматически; + хронология health |
| Зависит от Xray-канала | нет | нет | нет (SSH); если SSH тоже недоступен — это улика «адрес недоступен целиком» |
| Новый код сервера | нет | нет (`--json` уже есть) | `xm bridge` + sudoers + тест VPS |
| Права на сервере | — | владелец вручную, `sudo` | sudo без пароля на одну read-only команду |
| Поверхность атаки | — | файл с рук на руки | SSH-ключ владельца (уже есть), allowlist команд; новых портов и токенов нет |
| Участие пользователя | кнопка | две команды на VPS + перенос файла | кнопка + «Подключить» в клиенте в окне |
| Корреляция «моя попытка ↔ что видел сервер» | нет | по времени, вручную | по времени + флагу `ssh` (сеть SSH-сеанса = сеть ПК) + версии ядра из session_id |
| Надёжность | высокая | зависит от дисциплины | зависит от SSH; деградирует в 2 |
| Усилия | базовые | + импорт JSON | + SSH-клиент, sudoers, контракт |

Отброшенные подварианты:

- **Мост через `xm ui` API.** Панель рассчитана на браузер: токен в URL, сеанс с
  простоем, `api/run` под фоновые задачи. Для приложения проще и безопаснее `ssh … sudo -n xm
  bridge …` без токена на диске и без постоянной службы (открытый вопрос владельца о постоянной
  панели в HANDOFF §3.6 не затрагивается).
- **Отдельный диагностический API на публичном порту или через тоннель Xray.** Публичный —
  новый порт и отпечаток (нарушает «наружу — только 443, всё отвечает как маска»); через
  Xray — недоступен ровно тогда, когда нужен.
- **Фоновый агент на ПК с постоянными пробами.** Регулярные TLS-хендшейки к серверу —
  паттерн; к тому же приложение с ядром Xray внутри и постоянной активностью — то, что ищут
  сервисы, обязанные выявлять VPN. Только по кнопке.

**Вывод:** вариант 3 как основной путь, 1 — всегда и первым, 2 — резерв. Приложение обязано
дать полезный вердикт в варианте 1 без единого байта от сервера.

## 3. Рекомендованная архитектура и обоснование

### 3.1. Принципы

1. **Сначала улики, потом вывод.** Каждая проверка кладёт в хранилище улику с источником,
   временем и надёжностью; правила читают только улики. Никаких выводов «по конфигу», где
   наблюдаемо следствие (урок «Признак брался из конфига», `lessons.md`).
2. **Сравнение с эталоном.** Сеть ПК проверяется парами: сервер ↔ эталонный хост той же
   категории; SNI маски на адресе сервера ↔ на настоящем адресе маски; Hiddify ↔ эталонное
   ядро с тем же профилем. Различие — улика, совпадение — исключение гипотезы.
3. **Одна причина наверху, остальное — под ней.** Как у `xm doctor`: первая по порядку
   стека (клиент → профиль → ОС → сеть → сервер), с «исключено» списком.
4. **Не провоцировать.** Бюджет проб к серверу (приложение C), ни одного изменения сетевой
   конфигурации, ни одного нового слушающего сокета наружу.
5. **Секреты и адреса не покидают ПК**, сервер отдаёт только числа, коды и хэши.

### 3.2. Эталонное ядро — центральное решение

Xray-core импортируется как Go-модуль (`github.com/xtls/xray-core/core`) и поднимается в
процессе на время одной пробы: outbound VLESS+REALITY+XHTTP с профилем пользователя, без
inbound, без локального SOCKS — соединение открывается через внутренний `dialer`
приложения, один запрос `GET /generate_204` и закрытие. Что это даёт:

- **Разделение «клиент ↔ всё остальное».** Эталон прошёл → сервер слушает, UFW открыт, путь
  пропускает ClientHello с X25519MLKEM768, профиль принят REALITY, UUID есть на сервере,
  XHTTP-путь верен. Тогда «таймаут» Hiddify — в Hiddify: ядро, служба, TUN, его разбор URI.
- **Распознавание отказа REALITY без сервера.** По ошибкам ядра: `received real certificate`
  → сервер жив и отдаёт маску, но профиль или правило долей не прошли; `Current fingerprint …
  does not support TLS 1.3` → профиль; таймаут на `HandshakeContext` → сеть/путь.
- **Классы заморозки с клиента.** После `204` — чтение ~64 КБ с эталонного ресурса через
  тоннель: встало после хендшейка / на 1–10 КБ / на 10–32 КБ — те же границы, что
  `health.py` (`HELLO_MAX`, `F16_MIN/F16_MAX`), только с другой стороны.
- **Отпечаток, который примет сервер:** `fp=chrome` (X25519MLKEM768 с v25.7.26). Версия ядра
  в приложении закрепляется в `rules/compat.yaml` и обновляется вместе с `landscape.md`
  (сейчас: любая ≥ v26.3.27; на v26.9.8+ открыта XTLS/Xray-core#6797 — для одиночной пробы
  без зависших хендшейков не проявляется, но версия всё равно фиксируется явно).

Цена: бинарник ~30 МБ, приложение формально содержит VPN-ядро (риск SmartScreen/AV, §10),
проба — это настоящий хендшейк к серверу и расходует бюджет.

```
│ Orchestrator: фазы, бюджет проб, согласия, таймауты              │
├──────────────────────────────────────────────────────────────────┤
│ Collectors (каждый — улики с id, source, reliability):           │
│  clients/hiddify   clients/v2rayn   os/windows   net/local       │
│  net/path (uTLS-пробы, сравнения)   probe/reference (Xray-core)  │
│  bridge/ssh (xm bridge facts|doctor|health)   bridge/manual      │
├──────────────────────────────────────────────────────────────────┤
│ Evidence store (сессия в памяти → DPAPI-файл)                    │
├──────────────────────────────────────────────────────────────────┤
│ Rules engine: гипотезы из rules/*.yaml + компилированные правила │
│  → Verdict {cause, confidence, evidence, ruled_out, next_checks} │
├──────────────────────────────────────────────────────────────────┤
│ Report: текст для человека, «Подробно», экспорт без секретов     │
└──────────────────────────────────────────────────────────────────┘
```

Адаптер клиента — интерфейс из пяти методов: `Detect()` (установлен ли, версия приложения и
ядра, режим TUN/прокси, каталог данных), `Profiles()` (профили → нормализованная модель без
секретов), `Logs(since)` (нормализованные события), `State()` (запущен ли, слушает ли локальный
прокси и на каком адресе), `Hints()` (известные особенности версии). Новый клиент — новый
пакет, остальное не меняется.

### 3.4. Почему именно так

- `xm doctor` уже умеет главное — повторить решение REALITY по ключу сервера и назвать стадию.
  Дублировать это на клиенте нельзя (нет приватного ключа) и не нужно: мост переносит его
  JSON как есть.
- Эталонное ядро закрывает ровно то, чего не хватает серверу: «клиент не шлёт» ↔ «клиент
  шлёт, но не доходит», и делает диагностику полезной без сервера.
- SSH уже является доверенным каналом владельца к серверу; добавлять второй канал — новая
  поверхность без выигрыша.

## 4. Взаимодействие Windows-клиента и `xm`

### 4.1. Сценарий «Диагностировать»

```
Фаза 0  Факты (≤ 2 с, без сети)
        адаптеры клиентов: версии, профили (хэши), состояние службы/TUN, свежие логи;
        ОС: адаптеры, маршруты, DNS, файрвол, AV, часы, прокси системы
Фаза 1  Локальная сеть и эталонные хосты (≤ 10 с, ≤ 8 соединений, к серверу — 0)
        DNS (UDP/53 ↔ DoH ↔ TCP/53 на одном имени), NCSI/204-эталоны, IPv6,
        настоящий адрес маски: TCP + TLS с SNI маски (это «обычный визит на сайт»)
Фаза 2  Сервер снаружи (≤ 15 с, к серверу: 1 TCP + 1 TLS + эталонная проба = 2 TLS)
        TCP на :443; TLS с SNI маски и fp chrome (uTLS): сертификат маски? стадия обрыва?;
        эталонная проба Xray-core: 204 + чтение 64 КБ (классы заморозки)
Фаза 3  Мост (если настроен и пользователь согласен; иначе — предложение ручного режима)
        ssh → sudo -n xm bridge facts (соль сессии через stdin) → сверка хэшей профиля,
        версия Xray, правило долей, часы;
        ssh → sudo -n xm bridge doctor --live 60: «нажмите Подключить в Hiddify ОДИН раз»;
        приложение в это окно к серверу не ходит (бюджет), в конце окна — ничего
        (эталонная проба уже была в фазе 2, doctor отличит её по версии ядра в session_id);
        ssh → sudo -n xm bridge health — хронология за 24 ч
Фаза 4  Вердикт, отчёт, запись сессии (DPAPI), предложение дополнительных проверок
        (UAC: захват pktmon ClientHello клиента; «повторить из другой сети»)
```

Все фазы прерываемы; каждая отдаёт улики, даже если следующая не состоялась. Фаза 3 без SSH
→ приложение показывает две команды для VPS и кнопку «Импортировать doctor.json».

### 4.2. Каналы

| Канал | Транспорт | Аутентификация | Что проходит | Когда |
|---|---|---|---|---|
| Эталонная проба | TCP → сервер:443, REALITY | профиль пользователя | 1 запрос 204, ≤ 64 КБ вниз | фаза 2 |
| TLS-зонд | TCP → сервер:443, uTLS chrome, SNI маски | нет | ClientHello, сертификат | фаза 2 |
| Мост | `ssh.exe` (OpenSSH Windows) → `sudo -n xm bridge …` | ключ владельца, known_hosts | JSON без секретов и адресов; на сервер — соль сессии (32 hex) | фаза 3 |
| Ручной обмен | файл | — | тот же JSON | резерв |
| Эталонные хосты | HTTPS | нет | `generate_204`, NCSI, 64 КБ ресурс | фазы 1–2 |

Через мост на сервер уходит только соль (для HMAC хэшей профиля) и длительность окна. Имя
хоста/порт SSH берутся из `~/.ssh/config` (алиас, как `xm-ui` в README) — приложение не
хранит ни ключей, ни паролей.

### 4.3. Контракт

- Каждый JSON от сервера несёт `schema: {name, major, minor}` и `xm: {commit, version}`.
  Клиент принимает известный `major`, при большем `major` — «обновите приложение», при
  меньшем — «обновите xm: `sudo xm self-update`», и продолжает автономно.
- `xm doctor --json` и `xm health --json` получают поле `schema` (добавление, совместимое с
  панелью).
- Новое `xm bridge facts` — приложение B.
- JSON Schema контрактов хранится в `xray/contracts/*.schema.json`; на сервере
  `tests/test-bridge.sh` валидирует вывод по схеме на фикстурах, в клиенте те же схемы и
  обезличенные фикстуры с реального сервера — в `testdata/server/`.

## 5. Компоненты и репозитории

### 5.1. Решение: `xray_client` отдельно, контракт в `xray`

| Критерий | Один репозиторий `xray` | Отдельный `xray_client` |
|---|---|---|
| Хуки и правила `xray` (`read-guard`, `commit-guard`, `tests/check.sh`, бюджет ответов, VPS-проверка каждой правки `ui/`) | рассчитаны на bash+python сервера; Go-приложение с CI под Windows и 30 МБ бинарниками их только мешает | свои правила: `go vet`, тесты на фикстурах, сборка под Windows |
| Релизы | релиза нет: `xm self-update` тянет ветку | GitHub Releases с подписанным `.exe` |
| Публичность и данные установки | те же запреты | те же запреты (AGENTS.md клиентского репо повторяет раздел «данные установки — никогда») |
| Контракт | в одном дереве | схемы + фикстуры, тест в обоих |
| Экспертиза (`landscape.md`, `lessons.md`) | один источник | клиентский репо не копирует текст: машинно-читаемый `rules/compat.yaml` с полем `source: landscape.md#строка` и датой; правка факта — в обоих, по правилу «инструкции меняются вместе с кодом» |

Вывод: `xray_client` — приложение; в `xray` — `xm bridge`, поле `schema`, `contracts/`,
`tests/vps/bridge.sh`, строка в `xm help`, абзац в README (одна команда для владельца).

### 5.2. Дерево `xray_client` (предложение)

### 5.3. Серверная сторона (в `xray`)

- `xm bridge facts|doctor [--live N]|health` — диспетчер с allowlist; аргументы проверяются
  регулярным выражением; `--live` ∈ [10, 120]; соль — 32 hex из stdin, иначе хэшей нет.
- `xm bridge on|off|status` — файл `/etc/sudoers.d/xm-bridge`:
  `<SUDO_USER> ALL=(root) NOPASSWD: /usr/local/bin/xm bridge facts, /usr/local/bin/xm bridge doctor, /usr/local/bin/xm bridge doctor --live [0-9]*, /usr/local/bin/xm bridge health`
  — без `*` после команды с аргументами, где это возможно; `visudo -c` перед установкой;
  `off` удаляет файл. Пользователь — тот, кто запустил `sudo xm bridge on`.
- Вывод `bridge` — только JSON, в stderr — ничего с адресами. `doctor` вызывается с `--json`
  и штатным путём (адреса — буквами, это уже доказано `tests/vps/doctor.sh`).
- Тест `tests/vps/bridge.sh`: `facts` валиден по схеме, хэши совпадают с пересчётом по
  `config.json` на той же соли, `bridge` не трогает `config.json` и Xray, `sudo -n` от
  пользователя владельца проходит для allowlist и падает для `xm restart`, `off` убирает файл.

### 5.4. Правила совместимости

| Что меняется | Кто обязан | Проверка |
|---|---|---|
| Поле добавлено в JSON сервера | minor++ в `xray`; клиент игнорирует неизвестные поля | схема с `additionalProperties: true` для верхнего уровня |
| Поле удалено/переименовано, смысл кода вердикта изменился | major++ в `xray`; клиент — релиз с поддержкой нового major | фикстура в `testdata/server/` + тест «старый major → автономный режим с предупреждением» |
| Новый код вердикта `xm doctor` | клиент показывает `title`/`actions` из JSON как есть (неизвестный код не ломает) | тест на неизвестный код |
| Новая версия Xray меняет правило REALITY | строка в `landscape.md` + `compat.yaml` + `mlkem_rule` в `facts` считается сервером по его версии (как в `doctor.py`) | клиент доверяет серверу, а не своей таблице, когда сервер доступен |

### 6.3. Локальная сеть и эталоны (L2)

| ID | Проверка | Данные | Стоимость | Что подтверждает / снимает |
|---|---|---|---|---|
| N1 | Есть интернет вообще | NCSI (`www.msftconnecttest.com/connecttest.txt`), `generate_204` двух CDN | 0 к серверу | исключает `lan.noinet` — без этого ни одна гипотеза про блокировку не поднимается |
| N2 | Белый список мобильной сети | российский эталон доступен, зарубежные — нет, сервер — нет | 0 | `path.whitelist` — «вероятно»; «подтверждено» — только при воспроизведении на второй зарубежной паре и отсутствии SYN на сервере (S3) |
| N3 | DNS-подмена провайдера | одно заведомо блокируемое имя: UDP/53 ↔ TCP/53 ↔ DoH; разные ответы или NXDOMAIN только по UDP | 0 | `lan.dns.spoof` (landscape 2026-08-26) — не причина таймаута к IP-профилю, но причина «через тоннель сайт не открывается» при `geoip:ru → direct` по подменённому адресу |
| N4 | Настоящий адрес маски: TCP + TLS с SNI маски, fp chrome | резолв маски, 1 соединение | 0 к серверу | эталон для P2: если и настоящий сайт недоступен — это не про наш сервер |

### 6.4. Путь до сервера (L3) — сравнительные пробы

| ID | Проверка | Данные | Стоимость | Что подтверждает / снимает |
|---|---|---|---|---|
| P1 | TCP на сервер:443 (и на порт SSH, если известен из `~/.ssh/config`) | время до SYN-ACK, RST/таймаут | 1 TCP (+1) | таймаут на обоих портах + N1 ок → `path.ip.unreachable` «вероятно» (бан IP / белый список / файрвол роутера); SSH ок, 443 — нет → `server.port` или фильтр по порту |
| P2 | TLS с SNI маски и uTLS chrome на адрес сервера | стадия: нет ответа на ClientHello / RST / сертификат маски получен | 1 TLS | сертификат маски → сервер жив, fallback работает; обрыв сразу после ClientHello ↔ N4 ок → `path.hello` «вероятно» (ТСПУ по SNI/сигнатуре) |
| P3 | Эталонная проба Xray-core (профиль пользователя) | результат: 204 / `received real certificate` / таймаут / обрыв на N КБ | 1 TLS + 64 КБ | `ok` (сервер и профиль работают → причина в клиенте или за тоннелем); `real certificate` → L5 или правило долей (различить может только S3); стадия обрыва после хендшейка → `path.freeze.post|mid|f16` «вероятно» |
| P4 | Повтор P1–P2 через 30 с один раз | сравнение | 1 TCP + 1 TLS | снимает единичную потерю; **в бюджет**: суммарно ≤ 3 TLS к серверу за 60 с |
| P5 | «Из другой сети» — по просьбе: пользователь переключает Wi-Fi ↔ телефон-модем, повтор фазы 2 | — | тот же бюджет в новом окне | различает ТСПУ оператора ↔ сервер/профиль: единственный способ «подтвердить» заморозку без сервера |

### 6.5. Сервер через мост (L4, L5, L3 с его стороны)

| ID | Проверка | Данные | Права | Что подтверждает / снимает |
|---|---|---|---|---|
| S1 | `bridge facts` | версия Xray, `mlkem_rule`, время, публичный порт, транспорт, fp из URI, UFW для порта, результат последней самопроверки health, хэши профиля на соли сессии | S | `server.*` по `_health_selfcheck`, `client.clock`, C4 |
| S2 | `bridge health` | `xm health --json`: последний трафик своих клиентов, инциденты, события (перезапуск, смена конфига, версия Xray) | S | хронология: «после обновления Xray до v26.10.21 трафик пропал» — `client.core.mlkem` «вероятно» даже без окна |
| S3 | `bridge doctor --live 60` в окне, пользователь жмёт «Подключить» один раз | JSON `xm doctor`: группы, `ssh` (сеть ПК), `own`, стадия, решение REALITY, версия ядра клиента, `after` | S | весь столбец «Что видит сервер» §1.2 — «подтверждено» |
| S4 | Самопроверка сервера по запросу (`facts --selftest`, до 40 с) | `_health_selfcheck` | S | `server.listen|dns|egress|handshake` |

### 6.6. За тоннелем (L6) — только если P3 = ok

| ID | Проверка | Данные | Что подтверждает / снимает |
|---|---|---|---|
| B1 | DNS через тоннель: имя через SOCKS-подобный путь эталонного ядра (`ATYP=DOMAIN`) | ответ есть/нет, время | `beyond.dns` (перехват `:53` на сервере, режим `nonIPQuery`) |
| B2 | Российский адрес через тоннель | ожидаемо blackhole (`xm harden --ru`) | объясняет «через VPN не открывается российский сайт»: не ошибка, а правило; проверка, что в клиенте `geoip:ru → direct` |
| B3 | Тест задержки клиента по URL | какой URL у клиента (Hiddify: настройка), доступен ли он напрямую | `beyond.latency_url`: клиент пишет «таймаут» по своему URL-тесту при живом тоннеле |

### 6.7. Что диагностируется где

| Класс | Только клиент | Нужен сервер | Принципиально недостоверно доступными средствами |
|---|---|---|---|
| L0 клиент (служба, TUN, порт, импорт, версия ядра) | да | — | — |
| L5 профиль: синтаксис | да | — | — |
| L5 профиль: совпадение с сервером (UUID, pbk, sid, path) | нет (эталон скажет лишь «не принят») | да (C4/S3) | — |
| L1 ОС, L2 локальная сеть | да | — | AV/WFP — только «возможно» без отключения модуля |
| L3: SYN не доходит | «вероятно» по P1+N1 | «подтверждено» — S3 (нет SYN от сети ПК) | бан IP ↔ белый список ↔ файрвол роутера различаются только проверкой из другой сети (P5) |
| L3: ClientHello режется / заморозка | «вероятно» по P2/P3 + N4 | «подтверждено» — S3 стадии `tcp|partial`, `after` | заморозка по отпечатку ↔ по SNI: без второй сети и без времени не различимы; причину заморозки (ASN, подсеть) ТСПУ не сообщает |
| L4 сервер | «сервер жив» по сертификату маски (P2) | всё остальное — S1/S4 | — |
| L6 за тоннелем | да (B1–B3) | режим `nonIPQuery` — `facts` | — |

## 7. Модель диагностических результатов и оценки уверенности

### 7.1. Таксономия причин (расширяемая, `rules/taxonomy.yaml`)

```
client.core.mlkem        ядро клиента без X25519MLKEM768 (sing-box/Hiddify 4.x, mihomo, Xray < v25.7.26)
```

Коды `xm doctor` отображаются 1:1 (приложение A); новые коды сервера показываются как есть.

### 7.2. Улика и гипотеза

```yaml
Evidence:
  id: P2.tls            # проверка и подпроверка
  source: client|server|reference|user|log
  at: 2026-10-28T12:00:05+03:00
  value: {stage: "hello_sent", outcome: "timeout", ms: 10000}
  reliability: high|medium|low   # high — наблюдение; medium — лог/таблица версий; low — слова пользователя
  redacted: true                 # значение прошло редактор секретов

Hypothesis:
  code: path.hello
  requires: [N1.ok, N4.ok, P2.timeout_after_hello]     # все — иначе гипотеза не поднимается
  supports:  [S3.stage.tcp|partial, P5.other_network.ok, C7.syn_seen]
  contradicts: [P3.ok, S3.stage.hello, S3.rd.ok]
  confidence:
    confirmed: requires + любой из [S3.*, P5.*]
    likely:    requires + 0 supports, 0 contradicts
    possible:  requires частично (не хватает улики X)
    excluded:  contradicts
  next_checks: [S3, P5]                                 # что добьёт до «подтверждено»
  text: {title, why, actions}
```

Уверенность — четыре ординальных уровня, без процентов: «подтверждено» — есть наблюдение с
обеих сторон или воспроизведение из второй сети; «вероятно» — наблюдение с одной стороны и
эталон снял альтернативы; «возможно» — только косвенные улики (таблица версий, лог, слова);
«исключено». Вердикт — первая гипотеза по порядку стека с уровнем ≥ «вероятно»; если такой
нет — `unknown.*` с конкретным списком `next_checks` (это и есть «какие дополнительные проверки
нужны»). Несколько «подтверждённых» одновременно — верхняя по стеку главная, остальные —
«также найдено».

### 7.3. Защита от ложной «блокировки»

Гипотеза класса `path.*` не поднимается, пока не выполнены: N1 (интернет есть), N4
(настоящая маска доступна) или эталонный зарубежный хост доступен, попытка воспроизведена
дважды (P4). «Подтверждено» — только S3 или P5. Текст вердикта при «вероятно» всегда содержит
альтернативу и проверку: «Это похоже на блокировку по пути, но то же даст сломанный роутер
или бан адреса. Подтвердить: переключиться на мобильный интернет и повторить» — по правилу
`xray-dpi`: назвать режим цензора и проверку, отличающую его от ошибки конфига.

### 7.4. Выход для пользователя

Пять блоков постановки: «Что не работает» (одна фраза), «Где» (уровень), «Причины:
подтверждено / вероятно», «Улики» (3–5 строк, человеческим языком, каждая — ссылка на
подробности), «Что делать» (1–3 действия; команда для VPS — копируемым блоком), «Если не
помогло» (`next_checks`). Технические подробности — отдельная вкладка: все улики с временем и
значениями, JSON сессии.

## 8. Механизм безопасного обмена и локального хранения

### 8.1. Редактор секретов (на входе в хранилище улик)

| Данные | В памяти сессии | На диске (история) | В экспорте |
|---|---|---|---|
| UUID, pbk, shortId, path, URL подписки | HMAC-SHA256(соль сессии) | хэш | хэш (соль не сохраняется → хэши в экспорте необратимы и несопоставимы между сессиями) |
| Адрес сервера, порт, SNI | как есть (нужны пробам) | как есть под DPAPI | по умолчанию `server:443`, галочка «включить адрес» |
| Логи клиентов | как есть | отредактированные: IP → `A`, `B` по сетям (как в doctor), UUID/ключи → хэш | то же |
| Приватные ключи, пароли, `~/.ssh` | не читаются | — | — |
| JSON сервера | как есть (там секретов нет по построению) | DPAPI | как есть |

### 8.2. Хранилище

- `%LOCALAPPDATA%\xdiag\sessions\<id>.json.dpapi` — DPAPI (`CryptProtectData`, CurrentUser);
  индекс сессий — отдельный файл с датой и кодом вердикта.
- Срок хранения — 30 дней по умолчанию, настройка 0–365; «Удалить историю» — удаление всех
  файлов и индекса; честно: на SSD безвозвратность стирания не гарантируется, это сказано в UI.
- Никакой телеметрии, автообновление правил — только по явному согласию (запрос к GitHub
  раскрывает IP ПК GitHub, не сервер).

### 8.3. Мост

- Транспорт — системный `ssh.exe` (OpenSSH Client входит в Windows 11): используются
  `~/.ssh/config`, агент, `known_hosts`; приложение ключей не хранит и не читает. Флаги:
  `-o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15`. Хост не в `known_hosts`
  → приложение не отвечает «yes» само: показывает команду для первой проверки отпечатка.
- На сервере — `sudo -n xm bridge <cmd>`: нет правила → приложение показывает `sudo xm bridge
  on` и переключается в ручной режим. Пароль sudo приложение не принимает и не передаёт.
- Allowlist с обеих сторон: клиент умеет вызывать только три команды; `xm bridge` принимает
  только их и валидирует аргументы; вывод валидируется по JSON Schema до разбора.
- На сервер уходит только соль сессии (stdin) и длина окна. Ничего из профиля, логов и
  состояния ПК на сервер не передаётся.

### 8.4. Активные тесты

- Бюджет — приложение C; счётчик соединений к серверу ведётся в оркестраторе и показывается
  пользователю («к серверу: 2 из 3 за минуту»).
- Ничего не меняется: ни маршруты, ни DNS, ни файрвол, ни службы. Единственное
  административное действие — захват pktmon (C7): отдельное согласие с объяснением, фильтр
  по адресу и порту сервера, файл `.etl` удаляется сразу после разбора.
- Эталонное ядро не открывает слушающих сокетов и не меняет системный прокси.

## 10. Основные риски, ограничения и компромиссы

| # | Риск | Чем грозит | Смягчение |
|---|---|---|---|
| 1 | Диагностика сама провоцирует заморозку по отпечатку (> 3 TLS/60 с) | ложный `path.freeze`, 120–600 с без связи | бюджет C; одна попытка клиента в окне; xmux Hiddify может открыть до 3 соединений за попытку — считать по C7, предупреждать |
| 2 | Ложная «блокировка» | неверный совет менять хостер | §7.3: без N1/N4 и повторов гипотеза не поднимается; «подтверждено» только S3/P5 |
| 3 | Логи Hiddify 4.1.x на диске пусты, форматы меняются (PR #2333 в main, ветка v5 — другие пути) | адаптер слепнет | логи — улика средней надёжности; ядро диагностики не зависит от них; адаптер версионируется; кнопка «вставить экспорт логов» |

| 7 | Приложение с ядром Xray = «VPN-клиент» для сервисов, ищущих VPN | адрес сервера виден только серверу и эталонным хостам; к российским сервисам приложение не ходит через тоннель | эталонные хосты — зарубежные 204-эндпоинты; B2 только проверяет blackhole |
| 8 | `sudo` без пароля на `xm bridge` | расширение прав при компрометации ключа | allowlist без `*`, только чтение, `visudo -c`, `xm bridge off` |
| 9 | Два репозитория — дрейф контракта | тихая поломка моста | `schema`, фикстуры в обоих, тест «старый major → автономно» |
| 10 | SSH недоступен из сети с белым списком/баном | мост не работает ровно в худшем случае | это улика (P1 по порту SSH), ручной режим с телефона: `xm doctor --json` → файл |
| 11 | WebView2/`ssh.exe` отсутствуют | UI/мост не стартуют | проверка при запуске, подсказка; CLI работает без обоих |
| 12 | Корреляция по времени: часы ПК и сервера | попытка «не в окне» | W7 + `facts.time`; окно с запасом ±5 с; в doctor попытка ПК помечена `ssh` |
| 13 | Чтение `guiNDB.db` при работающем v2rayN | повреждение БД | только копия файла, только чтение |

Ограничения, которые не снимаются: причина бана IP/ASN и белого списка конфигом не лечится
(`landscape.md`, «Чего не обещать»); заморозка по отпечатку ↔ по SNI различимы только по
времени и второй сети; AV/WFP — только «возможно».

## 12. Критерии приёмки и стратегия тестирования без живого сервера

### 12.1. Уровни

### 12.2. Критерии приёмки (общие)

1. Без сервера и без сети приложение завершает сеанс вердиктом `lan.noinet` за ≤ 15 с, не
   падает и ничего не пишет на сервер.
2. Ни один тест и ни один сеанс не создаёт более 3 TLS-соединений к адресу сервера за 60 с
   (проверяется счётчиком оркестратора в тестах симулятора).
3. В экспорте нет UUID, pbk, shortId, path, URL подписки, IP (проверка регулярными
   выражениями из `tests/check.sh`, перенесёнными в клиентский репо).
4. Неизвестный `major` контракта, неизвестный код вердикта, пустой JSON — автономный режим с
   предупреждением, не сбой.
5. Каждая гипотеза с уровнем «вероятно» в тексте содержит альтернативу и `next_checks`.
6. Адаптер клиента при неизвестной версии отдаёт «частичная поддержка», остальные проверки
   выполняются.

## 13. Вопросы, критически влияющие на архитектуру

Для каждого — допущение, с которым проект продолжается, если ответа нет.

1. **Hiddify остаётся основным клиентом?** Сейчас он не проходит REALITY сервера (v26.10.21),
   исправление только в ветке v5. Если да — приложение в первую очередь должно уметь сказать
   «переключитесь на v2rayN» и распознать будущую v5 (другие пути и ядро). Допущение: да,
   оба клиента равноправны в MVP.
2. **SSH с ПК на сервер настроен и будет использоваться приложением?** Нужно: алиас в
   `~/.ssh/config`, ключ, согласие на `sudo` без пароля для `xm bridge`. Если нет — этап 3
   уходит в конец, ручной режим становится основным. Допущение: да (панель уже так работает).
3. **Допустимо ли правило `NOPASSWD` на `xm bridge` в sudoers?** Альтернатива — ввод пароля
   sudo при каждом сеансе (в приложение пароль не вводится: мост тогда через отдельный
   терминал). Допущение: допустимо для read-only allowlist.
4. **Эталонное ядро внутри приложения приемлемо?** Это ~30 МБ, настоящий хендшейк к серверу
   с профилем пользователя и риск AV. Альтернатива без эталона резко сужает автономную
   диагностику (строки 6–7 §1.2 только через сервер). Допущение: приемлемо.
5. **Подпись кода.** Без сертификата SmartScreen будет блокировать exe с ядром Xray.
   Варианты: самоподписанный + инструкция, покупка сертификата, сборка из исходников
   владельцем. Допущение: сборка владельцем из исходников через GitHub Actions, без подписи.
6. **Права администратора.** Можно ли по умолчанию запрашивать UAC для pktmon, или только по
   кнопке «углублённо»? Допущение: только по кнопке, после базового вердикта.
7. **Эталонные хосты.** Готовы ли вы, что приложение ходит на `msftconnecttest.com`,
   `gstatic.com`, настоящий адрес маски и один российский эталон (для белого списка)?
   Допущение: да; список редактируется в `rules/hosts.yaml`.
8. **Срок хранения и экспорт.** 30 дней и экспорт без адреса сервера по умолчанию — ок?
9. **Один ПК или несколько?** Если на разных ПК/сетях — история должна быть переносимой
   (экспорт/импорт сеансов). Допущение: один ПК.
10. **Язык интерфейса.** Русский, технические подробности — с английскими терминами. Ок?
11. **Канарейка для `xm health`** (регулярные пробы с ПК) — делать отдельным решением позже
    или не делать (паттерн регулярных хендшейков)? Допущение: позже, отдельно.
12. **`xray_client` — название и лицензия.** Репозиторий уже есть; имя бинарника `xdiag`
    — рабочее.

## Приложение C. Бюджет активных проб

| Цель | Лимит | Основание |
|---|---|---|
| TLS-хендшейки к адресу сервера | ≤ 3 за любые 60 с, включая эталонную пробу; в окне S3 — 0 от приложения | «заморозка по отпечатку»: > 3 параллельных TLS за 60 с → 120 с (`landscape.md`, 2026-05…06, отчёт) |
| TCP-соединения к серверу за сеанс | ≤ 6 за 5 минут | не выделяться; повтор P4 — один |
| Объём через эталонный тоннель | ≤ 64 КБ вниз, 1 запрос | классы заморозки 10–32 КБ (`health.py`) |
| Эталонные хосты | ≤ 8 соединений за сеанс | обычный фон браузера |
| Захват pktmon | ≤ 90 с, фильтр по адресу и порту сервера | только по согласию |
| Повтор сеанса | подсказка «подождите 2 минуты» после сеанса с `path.*` | не усугублять заморозку |
